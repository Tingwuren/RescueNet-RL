# 智能应急广播与通信资源配置与组网模块开发对接接口文档

## 文档说明

本文档基于当前代码实现整理，主要面向平台开发人员和联调人员，说明 `RescueNet-RL` 对外开放的接口路径、请求参数、响应结构、事件流格式以及使用时需要注意的约束条件。当前服务端采用 FastAPI 实现，统一接口前缀为 `/api`，默认通过 HTTP 传输 JSON 数据。文档内容以“现有实现已经支持什么”为准，而不是按未来规划进行描述，因此平台侧可直接依据本文档进行接口对接和联调。

当前实现尚未接入认证与授权能力，跨域策略也保持开放状态，因此在内网联调和前后端开发阶段使用较为方便。如果后续要接入正式业务平台，建议在网关或服务层补充统一鉴权、访问控制和审计策略。也就是说，本文档关注的是业务接口本身，而不是生产安全体系。如果平台已经有成熟的统一网关，那么最合理的方式通常是在网关侧补充鉴权、限流和审计，而让算法服务自身保持接口职责单一。

还需要说明的是，本文档描述的接口以算法服务为中心，因此很多字段都带有明显的“场景建模”和“策略仿真”语义。平台在对接时，不应简单把这些字段当作通用设备管理字段理解。例如本文中的 `x`、`y` 坐标默认表示区域网格索引，`coverage_ratio` 和 `broadcast_ratio` 表示策略评估指标，`scene_export` 则是为场景可视化服务而准备的结构化结果。

## 接口概览

系统当前提供五类核心能力接口，分别用于服务健康检查、场景元数据查询、训练任务发起、训练状态与过程监控，以及已有模型的灾情仿真。接口路径包括 `/api/health`、`/api/scenarios`、`/api/train`、`/api/train/{run_id}`、`/api/train/{run_id}/stream` 和 `/api/simulate`。其中前五个接口主要面向任务管理和训练监控，第六个接口主要面向在线推演和策略结果展示。

从平台接入流程上看，通常会先调用健康检查接口确认服务状态，再调用场景列表接口拉取基础配置，然后根据业务需要发起训练任务或者直接调用仿真接口。如果平台要实时展示训练过程，则还需要额外订阅训练事件流。也就是说，这套接口体系并不是彼此孤立的，而是天然适合组成“初始化、配置拉取、任务发起、过程监控、结果展示”这一条完整链路。

为了便于平台侧统一理解，有几个基础约定需要先说明。其一，`env_type` 当前只支持 `baseline` 和 `multimodal` 两种环境类型，其中平台实际接入时通常使用 `multimodal`。其二，`algorithm` 当前支持 `ppo`、`dqn`、`a3c` 和 `mppo` 四种算法。其三，所有 `x` 和 `y` 坐标在当前系统中都表示区域网格索引，其中 `x` 表示行号，`y` 表示列号，而不是实际米制坐标或经纬度。其四，仿真请求中的 `custom_base_stations` 如果传入 `null`，表示使用场景默认残余网络设定；如果传入空数组 `[]`，表示显式指定当前场景无残余网络；如果传入具体数组，则表示由调用方完全覆盖默认残余站点信息。

这些约定之所以重要，是因为它们直接决定了平台如何准备数据以及如何解释返回结果。特别是坐标语义和残余基站语义，如果平台在前端录入或后端拼装时理解错误，会导致仿真结果偏离预期。

## 健康检查接口

健康检查接口用于快速判断服务是否启动正常。调用方式为 `GET /api/health`，成功时返回一个最简 JSON 对象：

```json
{
  "status": "ok"
}
```

平台在初始化阶段可以优先调用该接口，作为连通性检查和服务可用性探针。在前端页面初始化、容器编排系统探活、任务调度前预检查等场景中，这个接口都非常适合使用。由于它不依赖场景数据、不依赖模型文件，也不触发复杂计算，因此响应通常非常快，适合作为平台侧的第一道可用性判断。

如果平台需要更完整的健康检查能力，例如同时检查数据文件是否存在、模型目录是否可访问、GPU 是否可用，那么应在后续版本中扩展专门的诊断接口。当前接口只表示服务进程和基础路由可用，不表示训练资源和模型资源一定完整。

## 场景列表查询接口

场景列表接口用于拉取当前系统中内置的灾害场景以及与之相关的环境和资源配置。调用方式为 `GET /api/scenarios`。该接口返回的数据既适合平台用来展示场景基础信息，也适合用来驱动前端表单中的场景下拉框、奖励模式下拉框、基站类型下拉框以及区域标签展示。

响应顶层结构如下：

```json
{

      "grid_size": 24,
      "region_grid": {

        "rows": 24,
        "cols": 24,
        "geo_bounds": {
          "lat_min": 21.8,
          "lat_max": 22.4,
          "lon_min": 113.3,
          "lon_max": 114.1
        },
        "cell_labels": {
          "6,8": "沿海居民聚集带"
        }
      },
      "num_users": 1500,
      "candidate_sites": 120,
      "max_steps": 72,
      "has_residual_network": true,
      "reward_profiles": [
        {
          "key": "coverage_balance",
          "label": "考虑覆盖",
          "description": "兼顾覆盖、吞吐与广播的折中方案，适合台风残余网络场景。",
          "coverage_weight": 1.0,

          "bandwidth_cost_weight": 0.15
        }
      ],
      "default_reward_profile": "coverage_balance",
      "base_stations": [
        {
          "name": "macro_bs",

          "supported_modes": [
            "5G_600MHz",
            "5G_700MHz"
          ]
        }
      ]
    }
  ]
}
```

其中，`name` 表示场景标识，`disaster_type` 表示灾害类型，`grid_size` 表示网格规模，`region_grid` 描述区域名称、行列数和经纬边界，`num_users` 表示场景中的用户规模，`candidate_sites` 表示候选部署点数量，`max_steps` 表示单回合最大部署步数，`has_residual_network` 表示场景默认是否存在残余网络。`reward_profiles` 用于描述该场景可选的奖励模式及其权重配置，`default_reward_profile` 表示默认采用的奖励模式，而 `base_stations` 则给出了当前场景可使用的基站类型、吞吐能力、服务能力、成本信息和支持的通信模式。

对平台集成来说，`region_grid` 可直接用于绘制区域概览和显示区域跨度，`reward_profiles` 可直接作为策略偏好配置源，`base_stations` 则适合直接驱动残余基站配置表单。更重要的是，平台不需要自行维护一份独立的场景元数据，只要在初始化或页面进入时拉取一次该接口，就能够保证前端配置界面与后端实际可用能力保持一致。

在实际联调过程中，这个接口通常是最值得优先对齐的接口。因为后续训练和仿真请求中涉及的大部分枚举值、场景名和基站名，都应来源于该接口返回值。如果平台绕开该接口，手工维护一套场景常量，那么后续很容易出现字段不一致或场景名拼写不一致的问题。

## 训练任务发起接口

训练任务通过 `POST /api/train` 发起。该接口是异步接口，调用成功后不会立即返回训练结果，而是返回一个训练任务编号 `run_id`，后续平台需要再配合状态接口和事件流接口持续跟踪任务进展。这种设计符合训练任务通常较长的执行特征，也避免了单个 HTTP 请求长期占用连接。

请求体示例如下：

```json
{
  "scenario_name": "typhoon_residual",
  "env_type": "multimodal",
  "algorithm": "ppo",
  "total_timesteps": 12000,
  "stochastic_eval": true,
  "reward_mode": "coverage_balance"
}
```

其中，`scenario_name` 是必填字段，表示训练要基于哪个灾害场景。`env_type` 默认为 `multimodal`，一般不建议平台切回 `baseline`，除非确实需要使用基础环境。`algorithm` 表示训练算法，当前只能取 `ppo`、`dqn`、`a3c` 或 `mppo`。`total_timesteps` 用于覆盖默认训练步数，当前后端要求该值不小于 `1000`。`stochastic_eval` 表示在训练过程中的评估阶段是否使用随机动作采样，当前多模态环境通常建议使用 `true`。`reward_mode` 仅在多模态环境下有效，用于指定奖励偏好；若不传，则沿用场景默认奖励模式。

调用成功后，接口响应示例如下：

```json
{
  "run_id": "4e871205b50c4a4ca617346ca260e7ce"
}
```

训练完成后，模型权重、训练指标、策略元信息和可视化曲线会默认写入 `artifacts/` 目录。如果当前环境类型为 `multimodal`，系统还会额外导出对应场景的组网方案 JSON。对平台来说，这意味着训练接口不只触发了一次计算任务，也间接触发了一次模型产物生成流程。因此，如果平台未来希望做“训练记录归档”或“模型版本管理”，最自然的切入点就是围绕这个接口的任务 ID 和产物目录展开。

在使用这一接口时，平台还应注意一个现实问题：训练任务本质上是资源型任务，尤其在步数较多或模型较大时，对 CPU、GPU 和内存都会有要求。因此，平台如果要开放给多人同时使用，最好在任务发起层增加并发控制和排队机制，而不是无限制地并发提交。

## 训练状态查询接口

训练状态接口通过 `GET /api/train/{run_id}` 调用，用来查询某个训练任务当前所处的执行状态。平台在不需要实时刷新细节时，可以通过轮询该接口的方式查看任务是否已完成或失败。对于后端管理页面、任务列表页或者非实时刷新场景，这个接口往往比事件流接口更适合使用。

响应示例如下：

```json
{
  "run_id": "4e871205b50c4a4ca617346ca260e7ce",
  "status": "running",
  "scenario_name": "typhoon_residual",
  "env_type": "multimodal",
  "algorithm": "ppo",
  "reward_mode": "coverage_balance",
  "started_at": 1742370000.123,
  "updated_at": 1742370008.456,
  "error": null
}
```

这里的 `status` 可能取值为 `pending`、`initializing`、`running`、`completed` 或 `failed`。`started_at` 和 `updated_at` 都是浮点时间戳，便于平台换算为本地时间。`error` 字段在失败时会携带错误信息，成功或进行中通常为 `null`。

从平台实现角度看，这个接口最重要的作用不是展示全部训练细节，而是提供一个稳定、幂等、适合轮询的任务状态视图。即使事件流因为网络中断而丢失，平台也可以通过该接口重新获知任务是否仍在执行。因此，状态接口应当被视为训练任务管理的“权威状态源”，而事件流更多承担“实时过程展示”的职责。

如果平台后续需要展示训练任务列表、按条件筛选任务或查看历史任务详情，那么未来还可以围绕当前状态接口继续扩展任务列表接口和任务详情接口。但在当前版本中，`run_id` 查询已经足以支撑基础联调。

## 训练过程事件流接口

如果平台需要实时展示训练过程中的回合指标、阶段性评估结果和状态变化，则应使用 `GET /api/train/{run_id}/stream` 接口。该接口返回类型为 `text/event-stream`，采用 SSE 机制向客户端持续推送事件。与传统轮询相比，SSE 更适合这种“训练过程中持续有增量消息产生”的场景，因为它能以更低的交互成本保持前后端实时同步。

每条消息都会以 `data:` 开头，内容为 JSON，例如：

```text
data: {"type":"update","payload":{...},"timestamp":1742370010.123}

```

当训练任务结束，且队列中的事件都被消费完成后，服务端还会追加一条结束消息：

```json
{
  "type": "end",
  "status": "completed"
}
```

当前事件流中的 `type` 主要有以下几种语义。`status` 用于表示任务阶段变化，例如从初始化进入运行，或从运行进入完成。`episode` 表示某个训练回合结束，消息中通常包含回合号、回合步数、累计奖励、覆盖率、广播率和终止原因。`update` 表示训练过程中一次统计更新；对于 PPO、A3C 和 MPPO，这类事件通常会带有更新轮次、平均奖励、平均覆盖率以及策略损失和价值损失，对于 DQN 则通常包含 `epsilon` 和 `q_loss`。`evaluation` 表示阶段性评估结果，通常包括当前环境步数、平均奖励、平均覆盖率和平均广播率。`completed` 表示训练器已经完成，消息中会包含总步数和累计回合数。`error` 用于表示训练过程中出现异常。

`episode` 事件示例如下：

```json
{
  "type": "episode",
  "payload": {
    "episode": 12,
    "steps": 72,
    "reward": 18.56,
    "coverage": 0.84,
    "broadcast": 0.79,
    "reason": "max_steps"
  },
  "timestamp": 1742370020.123
}
```

`update` 事件在 PPO/A3C/MPPO 下的常见格式如下：

```json
{
  "type": "update",
  "payload": {
    "update": 5,
    "step": 5120,
    "mean_reward": 12.8,
    "mean_coverage": 0.73,
    "loss_pi": 0.081,
    "loss_v": 0.264
  },
  "timestamp": 1742370030.123
}
```

`update` 事件在 DQN 下的常见格式如下：

```json
{
  "type": "update",
  "payload": {
    "step": 5000,
    "epsilon": 0.42,
    "mean_reward": 9.2,
    "mean_coverage": 0.61,
    "q_loss": 0.118
  },
  "timestamp": 1742370030.123
}
```

`evaluation` 事件示例如下：

```json
{
  "type": "evaluation",
  "payload": {
    "step": 5120,
    "avg_reward": 15.7,
    "avg_coverage": 0.81,
    "avg_broadcast": 0.76
  },
  "timestamp": 1742370040.123
}
```

从平台实现角度看，最稳妥的方式是同时结合状态接口和事件流接口使用。状态接口适合做结果兜底，事件流接口适合做实时展示。在 UI 层，如果事件流断开，平台可以自动回退到状态轮询，再在网络恢复后重连事件流。这样可以让任务监控页面既有实时性，也有鲁棒性。

还需要注意，SSE 是单向流，因此客户端通常只负责接收消息而不在同一连接上发送指令。如果平台后续需要做暂停训练、取消训练、重试训练等操作，则应单独设计对应的控制接口，而不是复用当前事件流连接。

## 策略仿真接口

策略仿真通过 `POST /api/simulate` 调用。该接口会根据请求中指定的模型权重、环境类型、算法类型和场景信息，加载对应策略并执行若干回合评估，同时返回详细的恢复过程报告和场景导出结果。该接口是平台侧最核心的业务对接接口之一，因为它直接对应“输入一组灾情，输出一套恢复结果”这一使用场景。

请求体示例如下：

```json
{
  "scenario_name": "typhoon_residual",
  "checkpoint_path": "artifacts/ppo_policy.pt",
  "env_type": "multimodal",
  "algorithm": "ppo",
  "episodes": 1,
  "stochastic_eval": true,
  "custom_devices": [
    {
      "x": 6,
      "y": 8,
      "demand": 18.0,
      "connected": false,
      "broadcast_served": false
    },
    {
      "x": 16,
      "y": 18,
      "demand": 12.0,
      "connected": false,
      "broadcast_served": false
    }
  ],
  "custom_base_stations": [
    {
      "x": 10,
      "y": 12,
      "base_station": "macro_bs",
      "mode": "5G_700MHz"
    }
  ]
}
```

其中，`scenario_name` 默认为 `typhoon_residual`，`checkpoint_path` 默认为 `artifacts/ppo_policy.pt`，`env_type` 默认为 `multimodal`，`algorithm` 默认为 `ppo`，`episodes` 最小值为 `1`，`stochastic_eval` 用于控制是否采用随机采样动作。`custom_devices` 用于传入自定义设备列表，每个设备需要提供网格坐标、需求带宽、初始联网状态和初始广播覆盖状态。`custom_base_stations` 用于传入自定义残余基站列表，每项需要提供基站所在网格位置、基站类型标识以及启用的通信模式。若 `mode` 不合法，系统会自动退回到该基站支持的首个通信模式。

这里还需要强调一点：如果 `custom_devices` 的数量少于场景默认用户数，系统只会覆盖前若干个用户，其余用户仍沿用环境初始化时随机生成的数据。因此，如果平台要完全控制某一次仿真的设备输入，最好传入完整的设备列表。反过来说，如果平台只想对部分关键点位做人工修正，也可以只传入一部分设备，让系统对剩余部分继续沿用场景默认采样逻辑。

响应体示例如下：

```json
{
  "avg_reward": 19.82,
  "avg_final_coverage": 0.86,
  "reports": [
    {
      "episode": 1,
      "scenario": {
        "name": "typhoon_residual",
        "disaster_type": "typhoon",
        "num_users": 1500,
        "max_steps": 72,
        "reward_mode": "coverage_balance",
        "reward_label": "考虑覆盖",
        "reward_description": "兼顾覆盖、吞吐与广播的折中方案，适合台风残余网络场景。"
      },
      "initial_state": {},
      "steps": [],
      "final_state": {},
      "total_reward": 19.82,
      "termination_reason": "max_steps",
      "steps_taken": 72
    }
  ],
  "scene_export": {
    "disaster_scene_path": "artifacts/scene_exports/typhoon_residual_episode_1_disaster_scene.json",
    "deployment_scene_path": "artifacts/scene_exports/typhoon_residual_episode_1_deployment_scene.json",
    "disaster_scene": {
      "map_width": 5000,
      "map_height": 5000,
      "nodes": []
    },
    "deployment_scene": {
      "map_width": 5000,
      "map_height": 5000,
      "nodes": []
    }
  }
}
```

响应中的 `avg_reward` 表示所有评估回合的平均累计奖励，`avg_final_coverage` 表示所有评估回合的平均最终通信覆盖率。`reports` 是逐回合的详细报告，`scene_export` 则是当前第一回合导出的场景结果。对于平台展示层，通常可以把 `avg_reward` 和 `avg_final_coverage` 放在总览区，把 `reports` 放在过程回放区，把 `scene_export` 放在地图可视化区。

在 `reports` 中，`scenario` 字段记录了场景名称、灾害类型、用户规模、步数限制以及当前采用的奖励模式。`initial_state` 与 `final_state` 中通常会包含 `coverage_ratio`、`broadcast_ratio`、`remaining_budget`、`total_users`、`avg_user_throughput`、`recent_throughput`、`device_cost`、`bandwidth_cost`、`reward_breakdown`、`residual_base_stations`、`connected_users`、`broadcast_served_users` 和 `user_details` 等字段。平台若要展示恢复前后对比，这两部分就是主要数据来源。

`steps` 是策略执行过程中的逐步结果。每一步都会包含动作索引、本步奖励、本步执行后的状态，以及通信覆盖率和广播覆盖率的变化量。如果当前环境支持动作解码，系统还会在 `action_desc` 中补充动作语义，包括候选站点编号、通信模式编号、广播模式编号、对应网格位置、区域标签、通信模式名称和广播模式名称。平台如果希望实现可解释的“策略回放”，应重点使用这部分数据。对管理者而言，这一部分可以回答“系统做了什么”；对技术人员而言，这一部分可以回答“为什么会得到这样的最终效果”。

`scene_export` 中除了文件路径外，还直接返回了受灾场景和部署后场景的 JSON 内容。其结构基本如下：

```json
{
  "map_width": 5000,
  "map_height": 5000,
  "nodes": [
    {
      "id": 0,
      "type": "USER",
      "x": 1042,
      "y": 3125
    },
    {
      "id": 1,
      "type": "MACRO_ENB",
      "x": 2208,
      "y": 2917
    }
  ]
}
```

其中 `nodes[].type` 当前可能取值包括 `USER`、`MACRO_ENB` 和 `MANPACK_ENB`。平台如果需要绘制灾情节点图或部署后拓扑图，可以直接消费这一结构。由于系统同时返回文件路径和内联 JSON 内容，因此平台既可以即时展示，也可以在后续异步处理时读取产物文件。

还需要提醒一点，当前仿真接口并未开放 `reward_mode` 作为请求字段，这意味着仿真默认沿用场景已有的奖励偏好。如果平台未来确实希望在同一模型、同一场景下做多奖励偏好对比，则需要后续继续扩展接口和后端上下文配置。

## 错误处理说明

当前系统的常见返回状态包括 `200`、`404`、`422` 和 `500`。其中 `200` 表示请求成功，`404` 常见于训练任务不存在，例如查询了错误的 `run_id`，`422` 表示请求参数未通过 Pydantic 校验，`500` 则通常表示服务内部错误，例如模型文件不存在、模型结构不匹配或运行时异常。

当 `run_id` 不存在时，训练状态接口和训练流接口通常会返回如下结构：

```json
{
  "detail": "Training run not found."
}
```

平台在对接时，建议将 `422` 视为请求参数问题，将 `500` 视为服务端执行问题，并对 `checkpoint_path`、算法类型和场景名称做前置校验，以减少联调阶段的无效调用。特别是 `checkpoint_path`，它不是一个逻辑标识，而是服务端能够访问到的实际文件路径，因此平台侧不应把本地浏览器路径或前端虚拟路径直接传给服务端。

从实际联调经验来看，最容易出现的问题通常不是接口语法错误，而是语义不一致，例如场景名写错、算法类型与模型文件不匹配、网格坐标超出场景范围、基站类型不属于当前场景等。平台如果能在调用前基于 `/api/scenarios` 的结果做一次前置校验，很多问题都能在前端阶段提前拦截。

## 对接建议

实际对接时，建议平台先调用 `/api/health` 和 `/api/scenarios` 完成服务连通性检查和基础配置拉取，再基于场景信息构建前端配置页面或任务管理页面。训练相关功能建议使用“发起训练 + 查询状态 + 订阅事件流”的组合模式，以便同时满足实时展示和结果兜底。仿真相关功能建议直接复用场景接口中返回的 `reward_profiles`、`base_stations` 和 `region_grid` 作为表单和可视化数据源，从而避免平台自行维护一套重复配置。

如果平台业务中区分管理员、指挥员和普通查看用户，那么训练接口和仿真接口也可以考虑在平台层做权限区分。训练接口更适合由少量具备策略管理权限的角色使用，而仿真接口则更适合在较多业务人员之间开放，因为它更偏向结果推演和方案比较。

在页面实现上，也建议把“训练”和“仿真”分成两个独立心智模型。训练是面向模型生成和能力沉淀的长期任务，仿真是面向当前场景推演和结果解释的即时任务。把二者混在同一个表单中，往往会让普通用户难以理解。

## 典型集成流程

一个较为完整的集成流程通常如下。平台启动或页面进入后，首先调用健康检查接口确认算法服务可达。随后调用场景列表接口，拉取可用场景、奖励模式、基站类型和区域边界信息，用于初始化页面和表单。若用户需要训练新模型，则由平台调用训练发起接口获取 `run_id`，随后同时使用状态接口和事件流接口监控任务进展。训练完成后，平台可记录模型路径和训练指标，供后续业务复用。若用户需要基于已有模型进行推演，则平台组织场景参数、自定义设备和残余基站信息，调用仿真接口，接收详细报告和场景导出结果，并在页面上进行地图展示、步骤回放和指标汇总。

这一流程之所以值得明确写出，是因为它基本对应了平台的真实使用方式。平台并不是单独调用某一个接口，而是要把这些接口串起来形成完整的业务闭环。文档中明确这一点，有助于平台侧从一开始就用“系统联动”的方式设计交互，而不是把每个接口当成孤立的工具接口来理解。

## 当前内置场景参考

当前实现内置了三个主要场景，分别是 `typhoon_residual`、`flood_no_residual` 和 `earthquake_residual`。它们对应的灾害类型依次为 `typhoon`、`flood` 和 `earthquake`，默认奖励模式依次为 `coverage_balance`、`cost_priority` 和 `coverage_priority`。平台在做初始接入时，可以优先围绕这三个场景完成全链路联调。

从联调顺序上看，通常推荐先以 `typhoon_residual` 场景跑通最完整流程，因为该场景同时具备较完整的区域信息、残余网络前提和默认奖励配置，比较适合作为平台与算法服务之间的第一条样板链路。待这一链路稳定之后，再扩展到 `flood_no_residual` 和 `earthquake_residual`，用来验证无残余网络和不同奖励偏好下的表现差异。

## 结语

本文档描述的是当前代码仓库已经实现并实际可调用的接口行为，适合作为平台联调依据。如果后续系统增加鉴权、任务列表、任务清理、在线奖励模式切换或自定义算法接入能力，建议同步更新本文件，确保接口文档与实际实现保持一致。

从对接实践角度看，最关键的不是单个字段解释得多细，而是平台和算法服务在场景、坐标、资源和结果语义上保持一致。只要这一层语义对齐到位，当前接口已经足以支撑训练、监控、推演和结果展示的完整业务闭环。
