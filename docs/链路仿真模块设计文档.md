# 链路仿真模块设计文档

更新时间：2026-05-26

## 1. 背景与目标

根据 `meet/5.22下午/5月22日系统功能需求.docx` 的会议要求，链路仿真模块不再作为孤立的网络 trace 演示页面，而应成为“策略测试结果”和“场景回放结果”的链路侧证明模块。会议中明确提出：链路仿真需要和场景回放使用同一场景、同一批设备、同一策略结果，并且不要求展示完整拓扑，而是聚焦关键链路在灾害前、受损后、部署恢复后的指标变化。

因此，本模块的目标是：

1. 与一次策略测试结果和一次场景回放记录绑定，使用统一的 `replay_id` 作为查询、展示、下载和验收证据入口。
2. 将复杂链路拓扑简化为三类关键链路指标，满足前端演示和验收证明需求。
3. 复用当前项目已有的 Mahimahi、ns-3、场景回放产物和后端接口能力，形成可追溯的数据闭环。
4. 保留当前链路仿真页面已有的视觉风格和信息密度，在现有界面中接入真实后端数据。

## 2. 需求口径

### 2.1 会议要求

链路仿真页面应服务于场景回放过程中的通信能力验证，核心要求如下：

| 要求 | 设计解释 |
| --- | --- |
| 不展示完整网络拓扑 | 完整拓扑由场景回放模块负责，链路仿真只展示关键链路指标和日志 |
| 与场景回放对应 | 链路仿真使用同一个策略测试结果、同一个 `replay_id` 和同一条时间轴 |
| 按类型聚合 | 设备数量较多时不逐条链路展示，按设备类型、残余网络类型、回程链路类型聚合 |
| 能体现灾害和恢复 | 指标要能看到初始、受损、部署恢复三个阶段的变化 |
| 能支撑验收 | 前端页面、链路图表、链路日志、下载文件要能作为录屏和自测报告材料 |

### 2.2 三类关键链路

链路仿真统一输出以下三类链路组：

| 链路组 ID | 中文名称 | 说明 | 主要指标 |
| --- | --- | --- | --- |
| `user_access` | 现场设备到用户/终端的链路 | 无人机基站、车载基站、便携基站、卫星终端等现场部署设备到受灾用户或终端的接入能力 | 吞吐、负载、利用率、覆盖用户数、接入成功率 |
| `residual_network` | 残余网络链路 | 灾后仍可用的宏基站、微基站、专网基站、应急残余站点等网络能力 | 可用带宽、受损系数、通信成功率、剩余容量 |
| `backhaul` | 灾区到外界的回程链路 | 灾区内部网络到外部指挥中心、核心网、卫星回程或公网出口的连接能力 | 回程吞吐、利用率、拥塞程度、恢复状态 |

> 当前 `server/replay_manager.py` 已存在 `link_metrics.jsonl` 和 `/api/replay/sessions/{replay_id}/link-metrics` 能力，其中已有 `user_access`、`backhaul` 等聚合指标。后续应将 `broadcast` 类展示口径调整或归并为 `residual_network` 的子项，保证页面与会议提出的三类链路一致。

## 3. 当前项目实现盘点

### 3.1 已具备能力

| 模块 | 文件/接口 | 当前能力 |
| --- | --- | --- |
| 场景回放产物管理 | `server/replay_manager.py` | 生成 `metadata.json`、`frames.jsonl`、`nodes_full.jsonl`、`link_metrics.jsonl`、`replay.log`、`report.json` 等回放产物 |
| 场景回放接口 | `GET /api/replay/sessions`、`GET /api/replay/sessions/{replay_id}/frames`、`GET /api/replay/sessions/{replay_id}/link-metrics` | 已能按 `replay_id` 查询场景回放帧和链路指标 |
| 策略测试接口 | `POST /api/simulate`、`POST /api/simulate/stream` | 策略测试后返回 `replay_session_id` 和 `replay_session_path`，可作为链路仿真的入口 |
| Mahimahi trace 分析 | `server/mahimahi_manager.py`、`frontend/src/components/MahimahiSimulator.vue` | 可读取 `data/traces/*.trace`，输出容量、吞吐、发送速率和利用率等时间序列 |
| ns-3 实验接入 | `server/ns3_replay_manager.py`、`GET /api/experiments`、`POST /api/ns3/run` | 可启动 ns-3、导入 `trace.json` 到 SQLite，并展示实验记录 |
| 链路仿真页面 | `frontend/src/components/LinkSimulationPage.vue` | 已有状态卡、控制区、Mahimahi 卡片、ns-3 实验表和原生回放嵌入区域 |

### 3.2 主要差距

| 差距 | 影响 | 设计处理 |
| --- | --- | --- |
| Mahimahi 当前是独立 trace 演示 | 无法证明 trace 来自本次策略测试或本次灾害场景 | 作为辅助仿真引擎，优先展示与 `replay_id` 绑定后的链路指标 |
| ns-3 实验未绑定 `replay_id` | 实验记录与策略结果、场景回放无法互相追溯 | 在实验元数据中补充 `replay_id`、`scenario_id`、`simulation_id` |
| 链路组口径不完全匹配会议要求 | 页面可能展示过多底层链路或错误分组 | 后端统一输出三类链路组，前端只围绕三类指标组织主视图 |
| 链路仿真页面当前以工具状态为主 | 页面无法直接表达灾害恢复效果 | 增加“本次回放链路指标”主面板，Mahimahi/ns-3 下沉为引擎和诊断区 |

## 4. 模块定位

链路仿真模块定位为“同一次策略测试结果的链路侧回放视图”。它不重新生成场景，不独立选择灾害数据，也不替代场景回放的地图和节点动画。

推荐的数据关系如下：

```text
灾害数据导入
  -> 策略训练/测试
  -> 部署方案输出
  -> 场景回放 replay_id
  -> 链路仿真 replay_id
```

链路仿真的权威数据源为 `artifacts/replay_sessions/{replay_id}/link_metrics.jsonl`。Mahimahi 和 ns-3 用于补充底层链路容量分析、实验校准和原生 trace 查看，但页面主证明链路应优先从 `replay_id` 对应的回放产物读取。

## 5. 总体架构

```text
frontend/src/components/LinkSimulationPage.vue
  |-- 查询回放会话列表
  |-- 选择 replay_id / 默认使用最新完成回放
  |-- 查询链路指标、帧摘要、日志、下载地址
  |-- 展示三类关键链路图表、状态卡、事件日志
  |-- 保留 Mahimahi 和 ns-3 诊断区域

server/api.py
  |-- /api/replay/sessions
  |-- /api/replay/sessions/{replay_id}/link-metrics
  |-- /api/replay/sessions/{replay_id}/frames
  |-- /api/replay/sessions/{replay_id}/logs
  |-- /api/replay/sessions/{replay_id}/download
  |-- /api/mahimahi/*
  |-- /api/ns3/*

server/replay_manager.py
  |-- 生成并管理 replay session
  |-- 聚合三类链路指标
  |-- 输出 link_metrics.jsonl 和 replay.log

server/mahimahi_manager.py
  |-- trace 容量分析
  |-- 作为可选链路容量引擎

server/ns3_replay_manager.py
  |-- ns-3 trace 导入
  |-- 作为可选原生仿真和细节回放引擎
```

## 6. 数据模型设计

### 6.1 链路仿真会话

链路仿真不单独创造新的业务测试 ID，默认继承场景回放的 `replay_id`。如后续需要单独记录仿真配置，可增加 `link_simulation_id`，但必须保留与 `replay_id` 的一对一或多对一关系。

```json
{
  "replay_id": "replay_20260526_143012_abc123",
  "simulation_id": "sim_20260526_143000",
  "scenario_id": "typhoon_residual_network",
  "algorithm": "mppo",
  "source": "strategy_test",
  "created_at": "2026-05-26T14:30:12+08:00",

  "frame_count": 121,
  "node_count": 1200,
  "link_groups": ["user_access", "residual_network", "backhaul"]
}
```

### 6.3 阶段枚举

| `phase` | 含义 | 页面表现 |
| --- | --- | --- |
| `initial` | 灾前或灾后初始残余网络状态 | 展示基线容量和初始覆盖能力 |
| `damaged` | 灾害影响后，基站损毁或链路退化 | 展示吞吐下降、失败率升高、拥塞告警 |
| `deploying` | 策略开始调度设备，设备尚未完全生效 | 展示部署事件和链路恢复趋势 |
| `recovery` | 部署设备生效，网络能力恢复 | 展示成功率、覆盖用户数和回程能力提升 |
| `finished` | 回放结束 | 展示最终汇总和下载入口 |

## 8. 链路指标生成逻辑

### 8.1 输入

链路指标生成依赖以下输入：

| 输入 | 来源 | 说明 |
| --- | --- | --- |
| 灾害场景和残余网络 | 灾害数据导入、策略测试请求 | 决定初始网络损毁程度和残余网络类型 |
| 用户/终端分布 | 灾害数据集或测试配置 | 决定接入链路负载和覆盖用户数 |
| 部署方案 | 策略测试输出 | 决定何时、在哪个网格部署什么设备 |
| 设备类型字典 | `docs/设备类型字典.md`、后端枚举 | 决定设备容量、覆盖、回程能力 |
| 场景回放帧 | `frames.jsonl`、`nodes_full.jsonl` | 决定每个时间点设备状态和节点状态 |
| Mahimahi/ns-3 结果 | 可选引擎 | 用于校准容量曲线或提供底层 trace 支撑 |

### 8.2 聚合规则

链路仿真不要求精确到每条物理链路或每个坐标，而是按业务语义聚合：

1. `user_access` 按现场部署设备类型聚合，例如无人机基站、车载基站、便携基站、卫星终端。
2. `residual_network` 按残余网络类型聚合，例如残余宏基站、残余微基站、专网基站。
3. `backhaul` 按回程方式聚合，例如卫星回程、临时光纤、应急指挥车回程。

同一类型设备数量较多时，页面展示平均吞吐、平均利用率、总覆盖用户数、平均成功率，并在详情表中展示设备数量和受影响网格数。

### 8.3 指标计算口径

| 指标 | 计算口径 |
| --- | --- |
| `throughput_mbps` | 当前时间片成功承载业务量，优先取仿真输出；无精细仿真时按容量、用户负载和成功率估算 |
| `load_mbps` | 当前链路组承载的业务需求，可由用户数、业务类型和策略测试负载生成 |
| `available_capacity_mbps` | 当前链路组理论可用容量，受灾害损毁、设备类型和 Mahimahi/ns-3 trace 影响 |
| `utilization` | `throughput_mbps / available_capacity_mbps`，容量为 0 时按 0 处理并记录异常状态 |
| `success_rate` | 成功接入或成功传输比例，按用户接入成功、链路丢包和设备状态综合计算 |
| `covered_users` | 当前链路组覆盖或服务的用户/终端数量 |
| `damage_factor` | 灾害造成的容量衰减比例，用于残余网络链路 |
| `status` | `normal`、`degraded`、`congested`、`recovering`、`active`、`offline` 等展示状态 |

### 8.4 与部署方案的关系

部署方案文件只需要说明“在什么时间，将什么设备部署到什么网格”。链路仿真负责根据回放帧和网格状态计算链路指标，不要求部署方案提前给出精确坐标或链路容量曲线。

示例部署事件：

```json
{
  "time_s": 24,
  "grid_id": "G_12_08",
  "device_type": "UAV_BASE_STATION",
  "device_count": 2,
  "action": "deploy"
}
```

链路仿真在第 24 秒之后结合设备生效延迟、覆盖网格、用户负载和回程约束，更新 `user_access` 和 `backhaul` 两类指标。

## 9. 前端设计

### 9.1 页面原则

`frontend/src/components/LinkSimulationPage.vue` 保留当前页面的深色背景、状态卡、控制区、双栏卡片、实验表和 ns-3 原生回放区域，不改成简化页面。真实数据接入后，页面信息架构调整为：

```text
链路仿真页面
  1. 顶部状态卡
     - 当前 replay_id
     - 节点规模
     - 链路组数量
     - 最终恢复率 / 成功率

  2. 回放选择与控制区
     - 选择最近策略测试结果
     - 选择 replay_id
     - 播放 / 暂停 / 拖动时间轴
     - 下载链路日志和指标

  3. 三类关键链路主面板
     - 现场设备到用户/终端链路
     - 残余网络链路
     - 灾区到外界回程链路

  4. 时间序列图表
     - 吞吐
     - 利用率
     - 成功率
     - 覆盖用户数

  5. 链路事件日志
     - 灾害造成链路下降
     - 设备部署生效
     - 链路恢复
     - 拥塞或失败告警

  6. 引擎与诊断区
     - Mahimahi trace 能力回放
     - ns-3 实验记录
     - ns-3 原生回放界面
```

### 9.2 主视图数据绑定

页面加载流程：

1. 调用 `/api/replay/sessions` 获取可用回放会话，默认选择最近一次完成的策略测试结果。
2. 根据 `replay_id` 调用 `/api/replay/sessions/{replay_id}/link-metrics` 获取整段链路指标。
3. 调用 `/api/replay/sessions/{replay_id}/logs` 获取日志。
4. 播放时间轴时，根据当前 `frame_index` 从本地缓存的 `series` 取值；需要精确数据时调用 `?frame_index=` 单帧接口。
5. 与场景回放页面跳转时，通过 URL 查询参数传递 `replay_id` 和 `frame_index`。

推荐 URL：

```text
#/link-simulation?replay_id=replay_20260526_143012_abc123
#/replay?replay_id=replay_20260526_143012_abc123&frame_index=36
```

### 9.3 三类链路卡片

每类链路卡片应展示：

| 展示项 | 说明 |
| --- | --- |
| 当前状态 | 正常、受损、恢复中、拥塞、离线 |
| 当前吞吐 | Mbps，展示当前值和相对初始值变化 |
| 利用率 | 百分比，超过阈值时高亮 |
| 成功率 | 百分比，体现恢复效果 |
| 覆盖用户/设备数 | 展示该链路组服务规模 |
| 事件摘要 | 当前时间点最近一条事件 |

### 9.4 图表设计

首期不强依赖复杂图表库，可延续当前组件内 SVG 折线图实现。图表至少包含：

| 图表 | 数据 |
| --- | --- |
| 三类链路吞吐趋势 | `groups[].throughput_mbps` |
| 三类链路利用率趋势 | `groups[].utilization` |
| 成功率趋势 | `groups[].success_rate` |
| 覆盖用户数趋势 | `groups[].covered_users` |

图表的时间轴必须与场景回放帧一致。用户拖动时间轴时，链路卡片、图表高亮点和日志高亮应同步变化。

## 10. Mahimahi 与 ns-3 集成设计

### 10.1 Mahimahi

当前 Mahimahi 模块已经能解析 `data/traces/*.trace` 并生成容量、吞吐、发送速率曲线。链路仿真中建议这样使用：

| 阶段 | 用法 |
| --- | --- |
| P0 | 保留为页面右侧或下方的“链路容量诊断”卡片，不作为主证明数据 |
| P1 | 为每类链路组配置默认 trace，例如受损基站、临时中继、卫星回程 |
| P2 | 将 trace 名称和 `replay_id` 写入 `link_summary.json`，证明本次链路曲线来自指定场景 |

建议新增映射文件：

```json
{
  "replay_id": "replay_20260526_143012_abc123",
  "trace_mapping": {
    "user_access": "temp-relay",
    "residual_network": "damaged-station",
    "backhaul": "emergency-command"
  }
}
```

### 10.2 ns-3

当前 ns-3 模块能启动仿真、导入 `trace.json`、展示实验列表和原生回放。链路仿真中建议这样使用：

| 阶段 | 用法 |
| --- | --- |
| P0 | 保留 `ns-3` 状态、实验表和原生回放区域，作为底层实验入口 |
| P1 | 在 SQLite `experiments` 表或附加元数据中记录 `replay_id`、`scenario_id`、`algorithm` |
| P2 | 支持从链路仿真页面点击实验记录，跳转到同一时间点的 ns-3 原生回放 |

需要补齐的字段：

```json
{
  "experiment_id": 12,
  "replay_id": "replay_20260526_143012_abc123",
  "scenario_id": "typhoon_residual_network",
  "algorithm": "mppo",
  "trace_path": "ns-3.46.1/trace.json",
  "imported_at": "2026-05-26T14:33:00+08:00"
}
```

## 13. 验收与测试方案

### 13.1 功能验收

| 验收项 | 通过标准 |
| --- | --- |
| 能选择一次策略测试结果 | 页面能列出回放会话，并默认选择最近一次完成记录 |
| 能展示三类链路 | 页面固定展示现场设备到用户、残余网络、灾区到外界回程三类链路 |
| 能随时间变化 | 播放或拖动时间轴时，三类链路指标同步变化 |
| 能体现灾害恢复 | 指标能看到初始、受损、部署、生效、恢复的趋势 |
| 能下载证据 | 可以下载链路日志、链路指标或回放报告 |
| 能关联场景回放 | 链路仿真和场景回放使用同一个 `replay_id` |

### 13.2 接口测试

```bash
curl http://localhost:8000/api/replay/sessions
curl "http://localhost:8000/api/replay/sessions/{replay_id}/link-metrics"
curl "http://localhost:8000/api/replay/sessions/{replay_id}/link-metrics?frame_index=36"
curl "http://localhost:8000/api/replay/sessions/{replay_id}/logs?limit=200"
curl "http://localhost:8000/api/replay/sessions/{replay_id}/download?type=log"
```

检查点：

1. `link-metrics` 返回中存在 `user_access`、`residual_network`、`backhaul`。
2. 每个时间点至少包含吞吐、利用率、成功率、状态字段。
3. `frame_index` 查询结果与完整序列中同一帧一致。
4. 日志中存在灾害影响、设备部署、链路恢复事件。

### 13.3 页面测试

| 场景 | 检查点 |
| --- | --- |
| 无回放数据 | 页面展示空状态，不报错，保留 Mahimahi/ns-3 诊断入口 |
| 有 1 次回放 | 自动加载最新 `replay_id` 并展示指标 |
| 多次回放 | 可切换不同 `replay_id`，图表和日志同步刷新 |
| 1200 节点场景 | 页面不卡死，链路指标按组聚合，不逐节点渲染 |
| 链路拥塞 | 利用率超过阈值时卡片和日志有明显提示 |
| 下载产物 | 下载文件内容与当前 `replay_id` 一致 |

## 14. 与现有页面的兼容策略

当前 `LinkSimulationPage.vue` 页面已经具备较丰富的视觉结构，后续开发应遵循以下兼容原则：

1. 不移除顶部状态卡，只将卡片内容从“工具状态”扩展为“当前回放链路摘要 + 工具状态”。
2. 不移除 Mahimahi 组件，将其下沉为辅助容量诊断。
3. 不移除 ns-3 实验表和原生回放区域，将其作为底层实验追溯入口。
4. 主视图新增三类链路指标时，应复用当前卡片、深色面板、表格和按钮风格。
5. 页面默认展示真实 `replay_id` 指标；当后端没有回放数据时，才展示空状态或工具诊断。

## 15. 风险与约束

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| Mahimahi trace 与场景不匹配 | 录屏时难以证明链路曲线来自本次测试 | 主数据使用 `link_metrics.jsonl`，Mahimahi 作为辅助 |
| ns-3 原生实验未绑定 replay | 实验表无法追溯策略结果 | P1 增加 `replay_id` 元数据绑定 |
| 设备类型不统一 | 链路组聚合错误 | 以 `docs/设备类型字典.md` 和策略测试输出为统一口径 |
| 1200 节点渲染压力 | 页面性能下降 | 链路仿真只渲染聚合指标，节点详情交给场景回放 |
| 日志不够面向验收 | 自测报告材料不足 | 单独生成 `link_simulation.log`，输出中文业务事件 |

## 16. 结论

链路仿真模块应以 `replay_id` 为核心，把当前独立的 Mahimahi trace 演示、ns-3 实验记录和场景回放链路指标统一成一个可证明、可回放、可下载的链路侧验收模块。首期开发重点不是重新实现底层网络仿真，而是把当前已有的 `link_metrics.jsonl`、`/api/replay/sessions/{replay_id}/link-metrics` 和 `LinkSimulationPage.vue` 页面接成真实数据闭环，并按会议要求固定展示“现场设备到用户/终端链路、残余网络链路、灾区到外界回程链路”三类关键链路。
