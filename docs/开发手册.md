## 智能应急广播与通信资源配置与组网模块开发手册

------

**【系统英文全称：RescueNet Reinforcement Learning System】**

**【系统英文简称：RescueNet-RL】**

**【版本：0.1.0】**



# 一、项目背景

本项目面向国家重点研发计划课题“应急通信网络多维资源动态配置方法（课题编号：2024YFC3015301）”，用于支撑极端灾害条件下的广播与通信资源智能配置、组网方案生成、训练评估、链路仿真和验收验证工作。

当前项目已经形成“场景数据集 + 强化学习训练 + 策略仿真 + Mahimahi 链路分析 + ns-3 实验回放”的完整原型链路。前端开发的目标不是重新定义业务流程，而是围绕当前后端真实能力，完成页面编排、参数录入、过程展示和结果回放，使平台侧人员能够直接操作训练、测试和仿真能力。

## 1.1 系统基础说明

- 前端页面结构应参考当前原型和 `frontend/src/App.vue` 已定义的导航结构。

- 导航菜单结构应以“登录、首页、模型训练、策略测试、场景回放、链路仿真、设备管理”为准。

- 前端与后端联调统一使用 `/api` 前缀接口，当前项目未接入正式认证鉴权。

- 页面开发应以“先查场景元数据，再发起训练/仿真，再展示流式结果或回放结果”为主线，不应脱离后端真实接口另行设计数据来源。

## 1.2 前后端联调约束

- `GET /api/scenarios` 是所有页面的基础元数据入口，前端不要手工维护一套独立场景常量。

- 当前后端没有“登录接口”“训练取消接口”“场景文件上传入库接口”，前端设计时不要虚构这些流程。

- 训练过程和流式仿真过程统一通过 `text/event-stream` 消费，前端应支持断开提示和异常提示。

- 场景回放页当前以浏览器本地存储作为数据源，回放记录来自训练页或测试页自动生成的结果持久化。


# 二、前端开发说明

前端页面开发必须以 `frontend/public/prototype/菜单.html`、`登录.html`、`首页.html`、`模型训练.html`、`策略测试.html`、`场景回放.html`、`链路仿真.html`、`设备管理.html` 为唯一视觉基准。当前 `frontend/src/App.vue` 中存在“原型页面 + 接口注入 / 抽屉联调”的临时实现方式，该方式只用于验证后端能力；正式前端页面开发时，必须把真实接口能力落在原型页面对应位置，不得脱离原型另起布局。

6. GET /api/mahimahi/traces

## 2.3 模型训练页

用于发起训练任务并展示训练过程。

- 功能点：场景确认、算法选择、训练参数配置、训练启动、训练过程展示、训练结果回放生成

```
原型页面
1、页面必须与 `frontend/public/prototype/模型训练.html` 一致
2、保持原型中的纵向滚动式“模型训练面板”结构，不要改成步骤条向导页
3、保留原型中各段折叠/展开区、卡片区、参数区、结果区的上下顺序
4、页面顶部菜单仍使用 `菜单.html`

页面展示基础上的开发说明
1、场景信息导入区
   保持原型中“导入受灾区域信息”“导入应急设备信息”“导入组网算法信息”三块内容
   这三块当前不是文件上传流程，而是对真实场景、设备和算法信息的确认展示
   数据来源分别是：
   场景信息来自 `GET /api/scenarios` 返回的 `region_grid`、`candidate_site_preview`
   设备信息来自 `GET /api/scenarios` 返回的 `base_stations`
   算法信息来自前端固定枚举 `ppo / dqn / a3c / mppo`

2、算法选择区
   保持原型中算法卡片或算法选择器布局
   点击算法后更新当前训练算法

3、参数设置区
   保持原型中的基础参数和高级参数分组
   实际字段需要与后端训练接口一一对应：
   env_type、total_timesteps、stochastic_eval、reward_mode、learning_rate、discount_factor、batch_size、rollout_steps、entropy_coef、clip_range、eval_interval

4、训练监控区
   保持原型中训练状态、日志、指标趋势、结果面板的位置
   日志展示需要按时间追加，不能覆盖旧日志

5、训练结果区
   保持原型中的训练结果展示位
   训练完成后补充展示最新 checkpoint 摘要和自动生成的回放结果摘要

按钮动作
1、进入页面
   先加载场景列表
   再加载训练产物列表
   然后给当前场景填默认算法和默认奖励模式

2、点击“导入受灾区域信息”
   打开原型中的对应确认区或弹窗
   展示当前场景区域网格、受灾说明、候选站点等信息

3、点击“导入应急设备信息”
   打开原型中的对应确认区或弹窗
   展示当前场景设备清单

4、点击“导入组网算法信息”
   打开原型中的对应确认区或弹窗
   供用户选择训练算法

5、点击“开始训练”
   校验场景、算法和训练参数
   发起训练任务
   获取 `run_id` 后立即订阅训练 SSE

6、点击“停止训练”或“停止展示”
   当前只能关闭前端 SSE 监听和停止前端状态刷新
   不能真正取消服务端训练任务

7、训练完成后
   自动查询最新训练产物
   匹配本次训练的 checkpoint
   自动调用策略仿真接口生成一条训练回放记录

调用顺序
1. GET /api/scenarios
2. GET /api/train/artifacts
3. 用户确认场景、算法、奖励模式和训练参数
4. POST /api/train
   入参：
   scenario_name
   env_type
   algorithm
   total_timesteps
   stochastic_eval
   reward_mode
   learning_rate
   discount_factor
   batch_size
   rollout_steps
   entropy_coef
   clip_range
   eval_interval
5. 取得 run_id
6. EventSource 订阅 GET /api/train/{run_id}/stream
7. 前端持续展示 status / episode / update / evaluation 事件
8. 训练完成后，GET /api/train/latest-artifact
9. 如 latest-artifact 未命中，再 GET /api/train/artifacts
10. 找到 checkpoint_path 后，POST /api/simulate
    入参：
    scenario_name
    env_type = "multimodal"
    algorithm
    checkpoint_path
    reward_mode
    stochastic_eval = true
    eval_seed = 13
    episodes = 1
11. 将仿真结果写入浏览器本地回放记录，供场景回放页读取

说明
1、模型训练页虽然可以接真实接口，但视觉布局必须完全服从原型页
2、当前后端没有“取消训练接口”和“训练数据文件上传接口”，前端不要虚构这两类流程
```

## 2.4 策略测试页

用于基于已有训练权重进行场景导入和策略仿真。

- 功能点：场景导入、权重匹配、残余基站配置、流式仿真、结果导出、回放跳转

```
原型页面
1、页面必须与 `frontend/public/prototype/策略测试.html` 一致
2、保持原型中的“策略测试面板”、场景展示页签、测试终端区、结果区、导出区
3、不要把该页改成纯表单页或单独弹窗页
4、页面顶部菜单仍使用 `菜单.html`

页面展示基础上的开发说明
1、场景与算法选择区
   保持原型中场景选择、算法选择、权重匹配提示的位置
   场景列表来自 `GET /api/scenarios`
   权重列表来自 `GET /api/train/artifacts`
   前端需按“场景 + 算法”自动匹配 checkpoint_path

2、场景导入区
   保持原型中的“导入场景”动作位置
   点击后调用场景快照接口，展示导入后的场景

3、场景页签区
   保持原型中的“已导入场景”“部署后场景”两个页签
   已导入场景展示导入前快照
   部署后场景展示测试完成后的部署结果

4、残余基站配置区
   保持原型中的站点列表、类型、坐标、数量或模式输入项
   用户修改后需要重新请求场景快照

5、测试终端区
   保持原型中的终端日志窗口和状态提示
   前端按 SSE 逐条追加 status、log、result、error、end 事件

6、结果与导出区
   保持原型中结果指标、导出按钮、跳转回放按钮的位置
   可导出受灾场景 JSON、部署后场景 JSON
   可跳转到场景回放页查看本次结果

按钮动作
1、进入页面
   加载场景列表
   加载训练产物列表
   自动尝试为当前场景和默认算法匹配权重

2、点击“导入场景”
   根据当前场景和残余基站配置请求场景快照

3、切换场景
   重新匹配权重
   清空旧结果
   自动重新导入场景

4、切换算法
   重新匹配 checkpoint_path
   若没有对应权重，提示先到模型训练页训练

5、增加、删除或修改残余基站
   重新执行场景导入
   保证预览图与当前配置一致

6、点击“开始测试”
   若当前场景快照不是最新版本，先自动导入场景
   然后发起流式仿真

7、点击“导出受灾场景”或“导出部署后场景”
   将最近一次真实测试结果中的 scene_export 导出为 JSON

8、点击“场景回放”
   跳转到场景回放页

调用顺序
1. GET /api/scenarios
2. GET /api/train/artifacts
3. 根据当前场景和算法，在 artifacts 中匹配 checkpoint_path
4. POST /api/simulate/scene
   入参：
   scenario_name
   env_type = "multimodal"
   custom_base_stations = 当前残余基站配置
5. 若用户修改残余基站，重新执行 POST /api/simulate/scene
6. 点击“开始测试”后，POST /api/simulate/stream
   入参：
   scenario_name
   algorithm
   checkpoint_path
   env_type = "multimodal"
   stochastic_eval = true
   eval_seed
   episodes = 1
   custom_devices = 当前导入设备
   custom_base_stations = 当前残余基站配置
7. 前端按 SSE 流式消费 status / log / result / error / end
8. 收到 result 后更新部署后场景和评估指标
9. 将结果写入浏览器本地回放记录

说明
1、`custom_base_stations = null` 表示沿用默认残余网络
2、`custom_base_stations = []` 表示显式无残余网络
3、该页要严格按原型布局承接真实测试能力，不要新加独立浮层工作台
```

## 2.5 场景回放页

用于逐帧回放训练或测试生成的恢复过程。

- 功能点：选择回放记录、逐帧拖动、场景对比、指标查看

```
原型页面
1、页面必须与 `frontend/public/prototype/场景回放.html` 一致
2、保持原型中的“场景回放面板”、回放记录区、主回放舞台、帧轴或滑块、详情展示区
3、原型中如存在“选择回放场景”弹窗，应继续保留并用于选择本地记录
4、页面顶部菜单仍使用 `菜单.html`

页面展示基础上的开发说明
1、回放记录区
   保持原型中左侧或上方记录列表位置
   数据源不是后端接口，而是浏览器本地存储中的回放记录

2、主回放舞台区
   保持原型中的场景图显示位
   当前帧切换后同步刷新图片、站点状态和用户状态摘要

3、帧控制区
   保持原型中的时间轴、帧滑块、当前帧编号展示
   用户拖动时逐帧更新右侧详情

4、详情区
   保持原型中的覆盖率、广播可达率、设备数、用户数等信息展示位
   如果原型中有“策略测试记录”等标签，也应继续保留

按钮动作
1、进入页面
   读取本地回放记录
   若有默认记录则自动载入第一条

2、点击“刷新列表”或打开“选择回放场景”弹窗
   重新读取本地记录

3、点击某条回放记录
   将该记录设为当前活动记录
   从第一帧开始展示

4、拖动帧滑块
   切换当前帧
   实时刷新场景图和当前帧指标

调用顺序
1. 当前版本不调用后端接口
2. 从浏览器本地存储读取训练页或测试页生成的 replay session
3. 用户选择回放记录
4. 用户拖动帧滑块逐帧展示

说明
1、该页当前依赖本地回放数据，不是服务器端回放查询接口
2、如果后续需要多用户共享回放记录，应新增服务端回放持久化接口
```

## 2.6 链路仿真页

用于展示 ns-3 状态、实验记录和 Mahimahi Trace 仿真能力。

- 功能点：链路状态查看、ns-3 运行、实验导入、Trace 选择、Mahimahi 曲线展示、终端日志展示

```

## 3.3 训练任务管理

### 3.3.1 POST /api/train 发起训练任务

```
【入参说明】
1、请求模型为 server/schemas.py 中的 TrainRequest
2、主要字段如下：
   scenario_name 必填，场景名称，需与 /api/scenarios 中的 name 对应
   env_type 可选，baseline | multimodal，默认 multimodal
   algorithm 可选，ppo | dqn | a3c | mppo，默认 ppo
   total_timesteps 可选，>=1000
   stochastic_eval 可选，默认 true
   reward_mode 可选，奖励模式 key
   learning_rate 可选，>0
   discount_factor 可选，0<值<=1
   batch_size 可选，>=1
   rollout_steps 可选，>=1
   entropy_coef 可选，>=0
   clip_range 可选，>0
   eval_interval 可选，>=1

【处理逻辑】
1、调用 server/training_manager.py 中的 TrainingManager.start_run() 创建 TrainingRun
2、接口同步返回 run_id，训练主体在后台线程执行
3、后台线程会复制默认配置并按入参覆盖：
   experiment.env_type = env_type
   experiment.algorithm = algorithm
   multimodal_env.scenario_name = scenario_name
   multimodal_env.reward_mode = reward_mode
   train.total_timesteps = total_timesteps
   train.rollout_steps = rollout_steps
   train.eval_interval = eval_interval
   train.eval_deterministic = not stochastic_eval
4、算法参数覆盖规则：
   learning_rate -> config[algorithm].learning_rate
   discount_factor -> config[algorithm].gamma
   batch_size -> DQN 写入 dqn.batch_size，其他算法写入 mini_batch_size
   entropy_coef 仅对 ppo / a3c / mppo 生效
   clip_range 仅对 ppo / a3c / mppo 生效，映射为 clip_coef
5、每次训练都会创建独立产物目录：
   artifacts/runs/{algorithm}_{scenario_name}_{run_id}/
6、训练过程中会创建训练环境和评估环境各一个，并根据 algorithm 选择对应 Trainer：
   ppo -> PPOTrainer
   dqn -> DQNTrainer
   a3c -> A3CTrainer
   mppo -> MPPOTrainer
7、训练完成后写出：
   {algorithm}_policy.pt 或 dqn_policy.pt
   policy_meta.json
   training_metrics.json
   training_coverage_curve.png
8、若 env_type = multimodal，额外导出：
   broadcast_architecture_{scenario_name}.json
9、成功响应只返回 {"run_id": "..."}，不等待训练完成

说明
1、该接口当前不会在提交时同步校验 checkpoint、场景训练结果等内容
2、场景名非法、环境构建失败、训练过程异常都会在后台线程中失败，并通过状态接口或 SSE 体现
3、当前后端没有 cancel training 接口
```

### 3.3.3 GET /api/train/{run_id}/stream 订阅训练 SSE

```
【处理逻辑】
1、根据 run_id 获取 TrainingRun，查不到返回 404
2、接口返回 text/event-stream
3、事件体统一按 data: {json}\n\n 输出，不额外设置 event 名称
4、训练线程会持续向 run.events 写入事件，前端需自行解析 JSON 中的 type 与 payload
5、当前实现中的主要事件类型包括：
   status
   episode
   update
   evaluation
   completed
   error
6、status 事件 payload.state 主要包括：
   initializing
   running
   completed
7、episode 事件 payload 主要包括：
   episode
   steps
   reward
   coverage
   broadcast
   reason

【处理逻辑】
1、服务初始化时扫描 data/traces/*.trace

### 3.5.3 GET /api/mahimahi/traces/{trace_name} 获取单个 trace 分析结果

```
【处理逻辑】
1、入参：
   trace_name 路径参数
   duration_s 查询参数，默认 60
   window_ms 查询参数，默认 500
2、接口返回：
   name
   period_ms
   total_packets
   avg_throughput_mbps
   capacity
3、capacity 为时间片数组，每项结构为：
   time_s
   value
4、capacity 的计算方式为：
   按 window_ms 切片
   统计当前时间窗内的 packet 传输机会数
   按 1500 字节包大小换算 Mbps
5、trace_name 不存在时返回 404

### 3.5.4 POST /api/mahimahi/simulate 执行链路推导

```
【入参说明】
1、请求模型为 MahimahiSimulateRequest
2、主要字段：
   trace_name 必填
   duration_s 默认 60，范围 1~300
   rtt_ms 默认 80，范围 1~2000
   buffer_packets 默认 100，范围 1~10000
   window_ms 默认 500，范围 100~5000

【处理逻辑】
1、当前实现不会真正调用 mm-link 执行原生网络仿真
2、接口先基于 trace 生成 capacity 时间序列
3、再派生生成：
   throughput = capacity * 0.82
   sending_rate = capacity * 0.90
4、返回字段包括：
   trace_name
   duration_s
   rtt_ms
   buffer_packets
   window_ms
   mahimahi_native = false
   capacity
   throughput
   sending_rate
   stats
5、stats 主要包括：
   avg_capacity_mbps
   avg_throughput_mbps
   avg_sending_rate_mbps
   utilization
   loss_rate
   total_delivered_mb
6、trace 不存在时返回 404

说明
1、当前 Mahimahi 页面展示的是“基于 trace 的推导结果”，不是原生 mm-link 实测曲线
2、前端应保留对 mahimahi_native 字段的兼容，便于后续切换真实仿真
```

### 3.5.5 POST /api/mahimahi/simulate/stream 流式链路推导

```
【处理逻辑】
1、入参与 /api/mahimahi/simulate 一致
2、接口返回 text/event-stream
3、当前 SSE type 包括：
   status
   log
   data_chunk
   result
   error
   end
4、data_chunk 事件按时间序列切片推送，payload 主要包括：
   capacity
   throughput
   sending_rate
5、当前实现会把总序列大致切成 20 份逐批发送
6、result 事件 payload 只返回：
   stats
7、最终由 end 事件声明 completed 或 failed

```

## 3.6 ns-3 实验回放

### 3.6.1 启动与基础数据

```
【处理逻辑】
1、服务启动时自动执行 ns3_replay_manager.start()
2、start() 会先尝试导入 ns-3.46.1/trace.json
3、随后启动 watcher 线程，每 2 秒轮询一次 trace.json 是否出现新数据
4、若存在 trace.json，则延迟 1 秒后自动导入实验库
5、SQLite 数据库文件为：
   ns-3.46.1/simulation_history.db
6、当前数据库初始化表包括：
   experiments 实验主表
   frame_data 逐帧数据表
   node_stats 节点统计表
7、其中 node_stats 当前仅建表，接口层尚未写入实际统计数据
8、服务关闭时执行 ns3_replay_manager.stop() 停止 watcher
```

### 3.6.2 GET /api/ns3/status 获取 ns-3 状态

```
【处理逻辑】
1、接口返回 ns-3 运行状态与资源状态，主要字段包括：
   available
   running
   pid
   started_at
   last_finished_at
   last_exit_code
   last_error
   db_exists
   trace_exists
   experiment_count
   native_path
   log_path
2、available = ns3 启动脚本存在 且 ns-3 原生 index.html 存在
3、native_path 固定返回 /ns3-native/index.html
4、log_path 指向 ns-3.46.1/ns3_backend.log
```

### 3.6.3 POST /api/ns3/run 启动 ns-3 实验

```
【处理逻辑】
1、接口无业务入参
2、若当前已有 ns-3 进程在运行，则直接返回当前状态，不重复启动
3、若 ns-3.46.1/ns3 脚本不存在，则返回状态对象，并在 last_error 中写入错误信息
4、若脚本无执行权限，后端会自动补执行权限
5、启动命令固定为：
   ./ns3 configure
   ./ns3 build
   ./ns3 run scratch/disaster-pro
6、进程 stdout/stderr 会统一写入 ns-3.46.1/ns3_backend.log
7、接口返回值与 /api/ns3/status 基本一致

说明
1、当前接口不会直接返回 exp_id，实验数据需等待 trace.json 被导入后再通过 /api/experiments 查询
```

### 3.6.4 POST /api/import 手动导入 trace

```
【处理逻辑】
1、接口读取 ns-3.46.1/trace.json
2、导入前会做兼容处理：
   若内容末尾存在逗号则去掉
   若缺少开头 [ 则补齐

3、解析成功后：

7、接口返回：
   success

# 四、补充说明

## 4.1 前端开发注意事项

```
1、所有枚举值优先取自 /api/scenarios，不要在前端硬编码场景名和设备名
2、训练和仿真都存在长时任务，页面必须有 loading、失败提示和断流提示
3、SSE 连接断开后，应在界面上明确提示“连接中断”而不是误报训练失败
4、场景回放当前依赖浏览器本地存储，需考虑存储容量不足时的提示
5、当前项目更适合做研发联调平台，不适合直接按生产主数据系统方式设计
```
