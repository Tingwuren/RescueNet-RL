# 训练测试过程与结果输出规范

> 版本：v1.0  
> 日期：2026-05-26  
> 目的：规范模型训练、策略测试、部署方案输出和场景回放之间的数据边界，解决当前部署基站类型过少、类型不准确、部署方案与回放职责混用的问题。

## 一、核心原则

一次策略测试结果对应一次场景回放，但两者职责不同：

```text
模型训练：学习某一灾害场景下的部署策略
策略测试：执行一次策略，输出测试结果和网格级部署方案
部署方案：说明在什么时间步，将什么场景设备部署到哪个网格
场景回放：读取测试结果和部署方案，负责把网格转换为地图坐标并做动态展示
```

部署方案不输出精确经纬度，也不承担地图坐标换算。它只记录 `time_step + device + grid`。精确坐标、地图偏移、同网格多节点散点、链路动画和视觉效果都属于场景回放模块。

## 二、场景决定设备类型

策略测试不能使用固定的 `MACRO_ENB`、`MANPACK_ENB` 作为真实设备类型。它们只能作为前端视觉分类。真实部署设备必须来自当前场景配置：

```text
scenario.communication_modes
  -> scenario.mode_profiles[communication_mode].base_station
      -> scenario.base_station_profiles[base_station]
```

也就是说，模型动作选择的是“通信制式”，后端必须根据当前场景把通信制式解析为对应的场景设备。

## 三、训练过程规范

训练过程只负责学习策略，不直接生成部署方案文件。

### 3.1 训练输入

训练任务输入必须明确：

| 字段 | 说明 |
| --- | --- |
| `scenario_name` | 当前训练场景 |
| `algorithm` | 训练算法 |
| `reward_mode` | 奖励配置 |
| `evaluation_protocol` | 评估协议 |
| `total_timesteps` | 训练步数 |
| `dataset_import_ids` | 可选，外部灾害数据导入记录 |
| `enabled_device_types` | 当前场景允许的设备类型，来自场景配置 |

### 3.2 训练产物

训练完成后输出：

| 产物 | 说明 |
| --- | --- |
| `policy_meta.json` | 模型元信息，记录训练场景和算法 |
| `training_metrics.json` | 奖励、覆盖率、损失等训练曲线 |
| 模型权重 | 策略测试加载的 checkpoint |
| 组网架构 JSON | 场景级组网能力说明，不等同于一次测试部署方案 |

训练产物不应声明“某时间部署某设备到某网格”。这部分必须由策略测试阶段在一次具体测试中生成。

## 四、策略测试过程规范

策略测试是“加载一个已训练模型，执行一次或多次 episode，并生成可回放结果”的过程。

### 4.1 测试输入

策略测试请求应包含：

| 字段 | 说明 |
| --- | --- |
| `scenario_name` | 测试场景 |
| `checkpoint_path` | 模型权重路径 |
| `algorithm` | 模型算法 |
| `reward_mode` | 奖励模式 |
| `evaluation_protocol` | 评估协议 |
| `episodes` | 测试回合数 |
| `dataset_import_ids` | 本次测试使用的灾害数据来源 |
| `custom_base_stations` | 残余网络/场景设备配置 |
| `custom_devices` | 专用设备接入快照 |

### 4.2 动作解析

模型动作仍可以保持当前形式：

```text
action = site_index × communication_mode × broadcast_mode
```

但测试结果中的动作解释必须扩展为：

```json
{
  "site_index": 17,
  "location": [4, 6],
  "region_label": "低洼避险点",
  "comm_mode": "Satellite_Ka",
  "broadcast_mode": "emergency_broadcast",
  "base_station": "satellite_relay",
  "device_label": "卫星 Ka 中继",
  "device_type": "satellite_relay",
  "supported_modes": ["Satellite_Ka"]
}
```

这里的 `location` 是网格行列，不是经纬度。

## 五、测试结果输出规范

一次策略测试结果应作为一个完整测试记录，建议后续增加 `test_result_id` 或 `replay_id`。当前响应应至少包含：

```json
{
  "avg_reward": 18.4,
  "avg_final_coverage": 0.86,
  "reports": [],
  "deployment_plan": {},
  "scene_export": {}
}
```

### 5.1 `reports`

`reports` 保留算法执行细节，包括：

| 字段 | 说明 |
| --- | --- |
| `scenario` | 场景、灾害类型、用户数、最大步数、奖励模式 |
| `initial_state` | 测试初态，用户连接、残余站点、覆盖率等 |
| `steps` | 每一步动作和步后状态 |
| `final_state` | 测试终态 |
| `deployment_plan` | 当前 episode 的部署方案 |
| `total_reward` | 总奖励 |
| `steps_taken` | 实际步数 |

### 5.2 `deployment_plan`

`deployment_plan` 是部署方案的权威数据。它必须使用网格级表达：

```json
{
  "schema_version": "rescuenet.deployment_plan.v1",
  "episode": 1,
  "scenario": {
    "name": "flood_no_residual",
    "disaster_type": "flood"
  },
  "summary": {
    "deployment_count": 12,
    "device_type_counts": {
      "satellite_relay": 3,
      "wifi_hotspot": 5,
      "mesh_uav": 4
    },
    "grid_precision": "region_grid_cell",
    "coordinate_policy": "scene_replay_resolves_coordinates"
  },
  "deployments": [
    {
      "sequence": 1,
      "time_step": 1,
      "site_index": 17,
      "grid": {"row": 4, "col": 6},
      "region_label": "低洼避险点",
      "device": {
        "base_station": "satellite_relay",
        "device_label": "卫星 Ka 中继",
        "device_type": "satellite_relay",
        "supported_modes": ["Satellite_Ka"],
        "coverage_radius": 4.4,
        "coverage_radius_km": 0.0,
        "max_users": 80,
        "max_throughput": 110.0
      },
      "communication_mode": "Satellite_Ka",
      "broadcast_mode": "emergency_broadcast",
      "reward": 0.82,
      "coverage_after": 0.54,
      "broadcast_after": 0.62,
      "remaining_budget_after": 9.0
    }
  ]
}
```

### 5.3 `scene_export`

`scene_export` 保留三个文件：

| 文件 | 作用 |
| --- | --- |
| `disaster_scene.json` | 测试输入/受灾场景快照 |
| `deployment_scene.json` | 部署后场景快照，供地图和回放预览使用 |
| `deployment_plan.json` | 网格级部署方案，供验收、复核和回放模块读取 |

前端“下载部署方案文件”应下载 `deployment_plan.json`，不应再把 `deployment_scene.json` 当作部署方案。

## 六、部署方案与场景回放分工

### 6.1 部署方案负责

部署方案只负责回答：

1. 第几个时间步部署？
2. 部署哪一种当前场景设备？
3. 使用哪种通信制式和广播制式？
4. 部署到哪个网格？
5. 部署后关键指标是多少？

### 6.2 场景回放负责

场景回放负责：

1. 根据 `grid.row/grid.col` 和 `effective_geo_bounds` 计算地图坐标。
2. 处理同网格多设备的偏移、散点和动画效果。
3. 绘制用户节点、残余站点、部署设备和链路。
4. 按 `time_step` 播放部署过程。
5. 输出回放日志和链路指标。

## 七、当前代码调整要求

本规范对应的实现要求：

| 要求 | 当前处理 |
| --- | --- |
| 动作解释增加场景设备字段 | `action_desc` 增加 `base_station`、`device_label`、`device_type` |
| 测试响应增加部署方案 | `SimulationResponse.deployment_plan` |
| 导出部署方案文件 | `scene_export.deployment_plan_path`、`scene_export.deployment_plan` |
| 前端下载部署方案 | 下载 `deployment_plan`，不是 `deployment_scene` |
| 部署后场景节点补充真实设备类型 | 节点增加 `device_type`、`device_label`、`node_role` |

## 八、验收口径

验收时应按以下方式说明：

1. 模型训练证明“策略可学习”。
2. 策略测试证明“模型可在具体场景下输出部署方案”。
3. 部署方案文件证明“什么时间部署什么设备到什么网格”。
4. 场景回放证明“部署方案如何在地图上落点并恢复通信”。
5. 链路仿真证明“恢复过程中的链路指标变化”。
