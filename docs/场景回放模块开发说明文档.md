# 场景回放模块开发说明文档

> 版本：v1.0  
> 日期：2026-05-26  
> 依据：`meet/5.22下午/5月22日系统功能需求.docx`、`meet/5.22下午/页面功能改造分模块说明.md`、`docs/测试大纲/指标/中期指标.md`、当前前后端实现

## 一、模块目标

### 1.1 背景

当前 `#/replay` 场景回放页面主要有两类展示：

1. `frontend/src/components/Ns3ReplayPanel.vue` 直接嵌入 `/ns3-native/index.html`，偏向 ns-3 原生动画页面。
2. `frontend/src/components/ReplayWorkbench.vue` 读取浏览器 `localStorage` 中的 `rescuenet.replaySessions`，播放训练或策略测试页面临时生成的压缩帧。

这两类能力都没有形成稳定的后端数据闭环。尤其是 `ReplayWorkbench` 的回放记录只存放在浏览器本地，换浏览器、清缓存或服务端重启后都无法作为验收证明；`Ns3ReplayPanel` 虽然有后端 ns-3 实验接口，但没有和策略仿真输出、灾害数据导入、专用设备接入、1200 用户节点日志绑定。

因此，本次改造目标是把场景回放从“前端动画/本地缓存”升级为“后端权威回放会话 + 前端逐帧交互展示 + 日志/节点清单可下载”。

### 1.2 验收证明链路

根据 5 月 22 日会议要求，场景回放模块需要承接前序功能，证明以下过程真实发生：

```text
灾害数据导入
  -> 策略仿真/测试
              -> 生成网格级部署方案和节点状态时序
          -> 后端保存回放会话
              -> 场景回放页按时间轴展示灾害受损、设备部署、通信恢复
                  -> 导出回放日志、完整节点清单、链路指标
```

模块必须能支撑中期指标中的相关证明点：

| 指标 | 场景回放模块证明方式 |
| --- | --- |
| 极端灾害通信资源变化数据集，通信制式种类不少于 4 类 | 回放会话记录 `dataset_import_ids`、灾害场景、受灾等级、4 类通信制式统计 |
| 初步实现资源优化调度仿真系统 | 回放策略仿真产物，展示策略部署节点和恢复过程 |
| 至少完成 1 种极端灾害条件下的数据仿真 | 会话元数据记录灾害场景和受灾等级，日志记录仿真输入与结果 |
| 至少实现专用设备接入功能 | 专用设备节点在回放地图、日志和节点清单中带 `device_id`、`device_type`、`is_dedicated` |
| 支持不少于 1200 个用户节点接入 | 页面显示完整节点数，前端可抽样绘制，后端日志和下载文件保留完整节点 ID |

## 二、会议需求落点

### 2.1 回放阶段

场景回放必须覆盖四个阶段：

| 阶段 | 页面表现 | 后端数据要求 |
| --- | --- | --- |
| 初始阶段 | 残余网络或正常网络处于可通信状态 | 初始用户节点、残余站点、初始覆盖率和通信成功率 |
| 灾害阶段 | 基础设施受损，链路中断，覆盖率/成功率下降 | 离线站点、失效链路、受灾等级、资源退化指标 |
| 部署阶段 | 策略推荐的应急设备按网格出现，回放模块再换算地图坐标 | `time_step`、`grid.row/grid.col`、场景设备类型、通信制式、广播制式 |
| 恢复阶段 | 通信链路逐步恢复，覆盖率和成功率上升 | 每帧用户连接状态、链路状态、覆盖率、吞吐、丢包率 |

### 2.2 页面展示要求

回放页需要展示：

| 展示项 | 说明 |
| --- | --- |
| 回放会话列表 | 从后端获取，不再只读浏览器本地缓存 |
| 场景信息 | 灾害类型、受灾等级、算法、模型产物、导入数据 `import_id` |
| 节点规模 | 完整用户节点数、当前绘制节点数、抽样比例 |
| 地图/拓扑 | 用户节点、残余站点、策略部署站点、专用设备节点、通信链路 |
| 时间轴 | 播放、暂停、重置、拖动到任意帧 |
| 指标卡片 | 覆盖率、通信成功率、在线节点数、失效链路数、已恢复链路数、专用设备生效数 |
| 事件日志 | 关键时间点、灾害发生、设备部署、覆盖恢复、链路变化 |
| 下载出口 | 回放日志、完整节点清单、帧数据、测试报告 |

### 2.3 与链路仿真的关系

链路仿真页面应与场景回放使用同一套 `replay_id` 和时间轴。场景回放负责展示“网络拓扑和节点状态”，链路仿真负责展示“关键链路指标”。

建议在回放会话中同时生成三类链路指标：

| 链路类型 | 数据粒度 | 指标 |
| --- | --- | --- |
| 现场设备到用户/终端链路 | 按设备类型或通信制式聚合 | 平均吞吐量、负载/利用率、成功率、丢包率 |
| 残余网络链路 | 按残余网络整体或通信制式聚合 | 剩余通信能力、成功率、可用带宽 |
| 灾区到外界回程链路 | 场景级聚合 | 回程吞吐、利用率、恢复状态 |

## 三、当前实现梳理

### 3.1 前端现状

| 文件 | 当前能力 | 差距 |
| --- | --- | --- |
| `frontend/src/App.vue` | `#/replay` 使用 `Ns3ReplayPanel` 作为主内容，侧边抽屉可打开 `ReplayWorkbench` | 主页面不是统一回放工作台，两个回放入口数据源不一致 |
| `frontend/src/components/Ns3ReplayPanel.vue` | 嵌入 `/ns3-native/index.html`，并对 iframe 做部分样式和阶段状态桥接 | 未直接消费策略仿真产物；不展示灾害导入、专用设备、完整节点日志 |
| `frontend/src/components/ReplayWorkbench.vue` | 读取 `listReplaySessions()`，按帧显示节点和指标 | 数据只在 `localStorage`，不是后端权威记录 |
| `frontend/src/utils/replaySessions.js` | 将 `SimulationResponse.reports[0]` 转为帧并压缩存储 | 只能前端转换，无法跨端共享，无法下载完整节点清单 |
| `frontend/src/components/CustomEnvironmentTester.vue`、`ScenarioTrainingPanel.vue` | 仿真/训练完成后调用 `saveReplaySessionFromSimulation` 保存本地回放 | 需要改为调用后端创建回放会话，并只把 `replay_id` 写入前端状态 |

### 3.2 后端现状

| 文件/接口 | 当前能力 | 差距 |
| --- | --- | --- |
| `POST /api/simulate` | 执行策略仿真，返回 `reports` 和 `scene_export` | 未自动持久化回放会话 |
| `POST /api/simulate/stream` | SSE 推送测试过程，最后返回 `SimulationResponse` | 过程日志未归档为回放日志 |
| `server/ns3_replay_manager.py` | 监听 `ns-3.46.1/trace.json`，导入 SQLite；提供实验列表、图表、单帧查询 | ns-3 实验与策略仿真结果没有统一 ID 和元数据绑定 |
| `GET /api/experiments`、`GET /api/exp/{id}/frame/{frame}` | 查询 ns-3 实验和帧 | 路径命名不够模块化，且字段不足以证明专用设备和灾害数据来源 |
| `GET/POST /api/disaster-imports` | 导入灾害数据，返回站点、热力图、独立用户数 | 仿真请求目前只记录 `dataset_import_ids`，未用它反向补全回放元数据 |
| 专用设备相关接口 | 支持设备 CRUD 和策略测试接入 | 回放节点和日志中需要进一步透出专用设备快照 |

### 3.3 已有可复用数据

| 来源 | 可复用字段 |
| --- | --- |
| `SimulationResponse.reports[0]` | `initial_state`、`steps`、`final_state`、`total_reward`、`coverage_ratio`、`broadcast_ratio`、`action_desc.location` |
| `scene_export` | `disaster_scene`、`deployment_scene`、`deployment_plan`，其中 `deployment_plan` 是“什么时间部署什么设备到什么网格”的权威方案 |
| `DisasterImportDetail` | `import_id`、灾害场景、受灾等级、`effective_geo_bounds`、`grid_size`、`station_counts`、`unique_user_count`、`deployments`、`user_heatmap` |
| `custom_devices` / 专用设备库 | `device_id`、`device_name`、`device_type`、`is_dedicated`、部署位置、能力参数 |
| `ns-3 trace` | `time`、`tp`、`loss`、`nodes`、`links` |
| `data/extreme_disaster_resources/regions.json` | 72 步资源变化时序，可补充通信制式级带宽/可用率趋势 |

## 四、总体设计

### 4.1 新增后端回放会话层

新增 `ReplaySessionManager`，建议文件为：

```text
server/replay_manager.py
```

职责：

1. 从策略仿真结果创建回放会话。
2. 把回放元数据、帧数据、节点清单、链路指标和日志持久化到后端。
3. 提供分页/按帧查询接口，避免一次性把全部节点和全部帧发给前端。
4. 提供下载接口，满足验收时“前端看不到的细节可由日志证明”。
5. 可选绑定 ns-3 实验 ID，使 ns-3 原生回放和策略回放能互相跳转。

推荐存储目录：

```text
artifacts/replay_sessions/
└── <replay_id>/
    ├── metadata.json
    ├── frames.jsonl
    ├── nodes_full.jsonl
    ├── link_metrics.jsonl
    ├── replay.log
    ├── scene_export/
    │   ├── disaster_scene.json
    │   ├── deployment_scene.json
    │   └── deployment_plan.json
    └── report.json
```

说明：

- `metadata.json` 用于快速列表查询。
- `frames.jsonl` 每行一帧，适合按帧号读取。
- `nodes_full.jsonl` 保留完整节点清单，前端默认只绘制抽样节点。
- `replay.log` 是验收材料，必须记录完整节点数、专用设备 ID、关键指标变化。
- 如果后续需要频繁按条件筛选，可再增加 SQLite 索引；第一期使用文件持久化即可满足开发和验收。

### 4.2 数据流

```text
策略测试页/模型训练页
  |
  | POST /api/simulate 或 /api/simulate/stream
  v
后端 evaluate_policy 生成 reports + scene_export
  |
  | ReplaySessionManager.create_from_simulation(...)
  v
artifacts/replay_sessions/<replay_id> 持久化
  |
  | 返回 replay_session_id
  v
前端进入 #/replay
  |
  | GET /api/replay/sessions
  | GET /api/replay/sessions/{replay_id}/frames/{frame_index}
  | GET /api/replay/sessions/{replay_id}/logs
  v
场景回放工作台播放后端帧数据
```

## 六、后端数据生成规则

### 6.1 从策略报告生成帧

当前 `frontend/src/utils/replaySessions.js` 已经有 `buildFramesFromReport(report)` 的前端实现。后端应将同类逻辑迁移到 `ReplaySessionManager`，但需要增加验收字段。

生成规则：

1. 从 `report.initial_state.user_details` 生成用户节点初始状态。
2. 从 `report.initial_state.residual_base_stations` 生成残余站点节点。
3. 从 `report.deployment_plan.deployments[*]` 读取网格级部署计划，并由回放模块换算为地图坐标。
4. 从 `report.steps[*].post_state.user_details` 更新用户连接状态。
5. 从 `post_state.coverage_ratio`、`broadcast_ratio`、`avg_user_throughput`、`remaining_budget` 生成指标。
6. 按最近站点或策略服务关系生成可视化链路。
7. 结合 `custom_devices` 或专用设备库快照，把专用设备节点标记为 `is_dedicated=true`。

### 6.2 阶段划分

如果仿真报告本身没有灾害前状态，后端应合成一个可解释的回放阶段：

| 阶段 | 生成方式 |
| --- | --- |
| `initial` | 使用 `initial_state`，表示受灾初始态或残余网络初始态 |
| `disaster` | 前 10% 帧或第一帧后若干帧，用更低覆盖率/更高失败率表现灾害冲击；若导入数据有 `level_4` 退化指标，则优先使用真实退化统计 |
| `deployment` | 策略动作逐步执行阶段，出现部署节点和专用设备 |
| `recovery` | 后 30% 帧，覆盖率、成功率、广播率趋近 `final_state` |
| `restored` | 最后一帧，输出最终指标和总结日志 |

注意：如果后续环境能直接输出灾害前、灾害中、恢复后的真实帧，应优先使用真实帧，不再合成阶段。

### 6.3 坐标规则

统一使用网格坐标作为可靠坐标来源：

```text
grid_position.row / grid_position.col
```

显示坐标由后端或前端按 `grid_size` 线性转换：

```text
x = (col + 0.5) / cols * map_width
y = (row + 0.5) / rows * map_height
```

如果需要经纬度地图，则使用 `DisasterImportDetail.effective_geo_bounds` 插值，不能直接使用部分数据集中的 `geo_position`，因为暴雨场景会出现多个站点经纬度完全重合的问题。

### 6.4 节点抽样

前端默认不绘制全部 1200+ 节点。后端按固定规则抽样，保证回放可复现：

```text
sampled = (stable_hash(node_id) % sample_ratio == 0) 或 节点为站点/专用设备/关键事件节点
```

要求：

- 专用设备节点永远返回。
- 新部署节点永远返回。
- 受灾/恢复状态变化节点优先返回。
- `node_counts.total` 必须记录完整节点数。
- `nodes_full.jsonl` 必须保留完整节点清单。

### 6.5 专用设备留痕

只要仿真请求中出现专用设备，回放会话必须记录：

```json
{
  "device_id": "DED-20260526-0001",
  "device_name": "应急通信车-01",
  "device_type": "Satellite_Ka",
  "is_dedicated": true,
  "source": "device_manager",
  "participated_frames": [12, 13, 14, 15]
}
```

日志至少包含：

```text
[time_step=12] 专用设备 DED-20260526-0001 参与部署，类型 Satellite_Ka，部署网格 row=4 col=6。
```

## 七、前端改造说明

### 7.1 页面结构

建议将 `#/replay` 主页面改为真实回放工作台，保留 ns-3 原生页面作为一个 Tab 或辅助入口。

页面分区：

```text
顶部：会话标题、场景/算法/数据来源、下载按钮
左侧：回放会话列表
中部：地图/拓扑回放画布
右侧：指标卡片 + 当前帧事件
底部：时间轴控制 + 回放日志
Tab：策略回放 / ns-3 原生回放 / 链路指标
```

### 7.2 `ReplayWorkbench.vue` 改造

当前 `ReplayWorkbench.vue` 应从本地缓存模式改为 API 模式：

| 当前逻辑 | 改造后逻辑 |
| --- | --- |
| `listReplaySessions()` 读 `localStorage` | `GET /api/replay/sessions` |
| `activeSession.frames[frameIndex]` 读前端数组 | `GET /api/replay/sessions/{replay_id}/frames/{frameIndex}` |
| 前端保存 `saveReplaySessionFromSimulation` | 后端返回 `replay_session_id` |
| 无下载 | 调用 `/download?type=...` |
| 无日志 | 调用 `/logs` |

建议保留 `localStorage` 只存最近选中的 `replay_id`，不要再存完整帧数据。

### 7.3 策略测试页联动

`CustomEnvironmentTester.vue` 和 `StrategyTesterPage.vue` 在收到仿真结果后：

1. 优先读取后端响应中的 `replay_session_id`。
2. 如果第一期后端还未自动创建，可临时调用：

```http
POST /api/replay/sessions
```

请求体包含 `scenario_name`、`algorithm`、`dataset_import_ids`、`custom_devices`、`simulation_result`。

3. 前端显示“测试结果已保存，可在回放页查看”，并跳转 `#/replay?replay_id=...`。

### 7.4 视觉标识

| 节点/链路 | 建议样式 |
| --- | --- |
| 普通用户节点 | 小圆点，按 connected/offline 区分颜色 |
| 残余基站 | 三角或基站图标，按 active/degraded/offline 区分 |
| 策略部署节点 | 高亮描边，出现时带短暂闪烁 |
| 专用设备节点 | 特殊颜色或图标，悬浮提示显示 `device_id` 和 `device_type` |
| 失效链路 | 灰色虚线 |
| 恢复链路 | 蓝/绿色实线 |

### 7.5 前端状态处理

必须处理以下状态：

| 状态 | 行为 |
| --- | --- |

## 十一、完成标准

第一期完成标准：

1. 回放会话由后端生成和持久化，前端不再依赖 `localStorage` 作为主数据源。
2. `#/replay` 能从 `/api/replay/sessions` 选择会话并逐帧播放。
3. 页面显示完整节点数、绘制节点数、抽样比例。
4. 回放日志能记录灾害数据来源、策略部署、指标变化和专用设备 ID。
5. 可下载回放日志和完整节点清单。
6. 至少一个极端灾害场景可以完成“导入数据 -> 策略测试 -> 回放 -> 下载证明材料”的闭环。

第二期增强目标：

1. 回放与 ns-3 实验双向绑定。
2. 链路仿真页面基于同一 `replay_id` 展示三类链路指标。
3. 地图从网格画布升级到经纬度地图，使用 `effective_geo_bounds` 做坐标映射。
4. 支持历史回放会话搜索、删除、归档和报告导出。

补充说明：部署方案文件不应输出精确经纬度或画布坐标，只输出时间步、场景设备类型和网格行列。精确落点、同网格散点、链路动画由场景回放模块根据 `effective_geo_bounds` 和地图视口计算。
