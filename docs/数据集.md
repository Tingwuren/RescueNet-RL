# 1. 极端灾害通信资源变化数据集

本章对当前项目使用的场景数据进行系统整理，形成“极端灾害通信资源变化数据集”的正式说明。数据集面向应急通信资源自适应部署任务，覆盖台风、洪水、地震三类典型极端灾害场景，当前包含 3 个可直接被训练环境读取的场景模板，并通过离散时间片刻画灾后通信资源从受损到逐步恢复的动态变化过程。

按场景划分，台风残余网络场景预设 1500 个用户规模和 120 个候选部署站点，洪水无残余网络场景预设 1280 个用户规模和 112 个候选部署站点，地震残余网络场景预设 1360 个用户规模和 128 个候选部署站点。三者共同构成当前数据集的任务规模基础。上述数值用于描述场景容量级别和决策空间大小，并不对应一组固定展开的静态样本；运行时环境会依据区域网格、用户簇和候选站点规模动态生成具体实例。

从资源覆盖范围看，数据集已经满足“通信制式种类不少于 4 类”的建设要求。当前场景共包含 8 类通信接入或中继制式：`5G_600MHz`、`5G_700MHz`、`5G_mmWave`、`Mesh_UAV`、`Satellite_Ka`、`Satellite_Ku`、`Shortwave_HF`、`WiFi6`，覆盖低频广覆盖、毫米波热点增强、卫星回传、局部接入、短波保底通信和空中中继等典型能力。同时，数据集还纳入 `digital_audio`、`emergency_loudspeaker`、`satellite_broadcast`、`terrestrial_dtv` 等广播资源，用于支撑灾情通告、公众预警和低交互业务分发。

## 1.1. 数据集建设目标与指标对齐

本数据集建设任务的核心要求，不是简单整理若干静态样本，而是围绕极端灾害条件下的应急广播与通信资源联合配置，形成一个可被训练环境直接读取、可支撑多灾害场景迁移、并能映射到后续组网验证的统一场景底座。就任务目标而言，数据集需要满足以下约束：一是通信制式覆盖不少于 4 类，能够体现 5G 600/700MHz、卫星、WiFi、短波等异构资源差异；二是能够支撑多种极端灾害场景下的训练与评估；三是能够表达残余网络和无残余网络两类起始条件；四是能够同时容纳广播方式和通信方式的联合调度需求。

结合当前项目实现，数据集建设目标可以归纳为四个层面。第一，在灾害类型上覆盖不同受损机理，当前已落地台风、洪水、地震 3 类典型场景，分别对应沿海残余公网协同恢复、无残余公网条件下从零建链，以及山区地形约束下的广覆盖与热点增强协同。第二，在通信资源种类上满足并超过“通信制式种类≥4”的中期要求，当前已配置 `5G_600MHz`、`5G_700MHz`、`5G_mmWave`、`Mesh_UAV`、`Satellite_Ka`、`Satellite_Ku`、`Shortwave_HF`、`WiFi6` 共 8 类通信接入或中继制式，同时补充 `digital_audio`、`emergency_loudspeaker`、`satellite_broadcast`、`terrestrial_dtv` 4 类广播资源，为广播与通信一体化调度提供建模基础。第三，在场景表达方式上，不采用逐用户逐时刻穷举记录，而采用“场景模板 + 动态采样”的组织方式，把区域网格、用户簇、候选部署规模、资源画像和时间片状态统一收敛为结构化模板，以支撑多轮训练和仿真回放。第四，在任务适配层面，数据集不仅要描述灾情背景，还要直接服务强化学习训练、策略测试、链路仿真和组网方案导出，因此必须同时表达用户需求、资源可用性、广播覆盖、成本约束和阶段性恢复过程。

对照上述建设要求，当前项目的数据集部分已经完成了关键基础能力建设。其一，通信制式数量达到 8 类，已明显超过“≥4 类”的下限要求；其二，场景模板同时覆盖残余网络和无残余网络两类条件，能够为残余网络协同恢复和从零建链两类任务提供直接数据支撑；其三，三类场景均已具备可供训练环境读取的 `communication_modes`、`broadcast_modes`、`time_series`、`base_stations` 和 `reward_profiles` 等核心字段，能够直接作为训练与评估输入；其四，广播资源与通信资源已在同一场景结构内统一建模，为后续一体化资源调度、组网分析和回放展示提供了共同数据底座。与此同时，当前版本的场景数量仍为 3 个，尚未扩展到更大范围的灾害分布，因此更适合作为当前阶段的正式训练数据基础，并为后续继续扩展场景类型和数量保留空间。

从本章职责边界来看，还需要明确“哪些指标由数据集直接承担，哪些指标由算法和系统共同承担”。例如，模型参数规模≥100 万或 ≥500 万、理论带宽资源利用率≥95%、单用户理论最大带宽≥40Mbps 等，最终体现于训练算法、资源调度策略和系统验证结果，而不是由数据集单独决定。数据集在其中承担的是底层约束建模职责：一方面通过多制式资源和多场景模板提供训练任务分布，另一方面通过用户规模、候选站点、设备能力、广播覆盖和时间片资源变化提供状态空间、动作空间和奖励计算基础。因此，本章与技术指标的关系不是“用文档重复指标”，而是把指标落到当前项目已经实现的数据结构、场景能力和可训练条件上。

**样本字段组织与建立方法**

数据集采用了“灾害模板 + 空间网格 + 用户簇 + 资源画像 + 关键时间片”的组合式建模方法。首先，围绕三类典型灾害建立场景模板，并为每个场景设定区域范围、网格尺度和是否存在残余网络。其次，使用用户簇而非逐用户明细来描述灾后需求分布，每个用户簇由中心位置、影响半径、空间密度和平均需求强度构成，用于模拟人口向安置点、港口、县城核心区等区域聚集后的非均匀需求。再次，通过通信制式画像和广播制式画像描述不同资源在覆盖半径、理论带宽、恢复速度和链路时延上的差异。最后，以关键时间片表达资源状态随灾情恢复逐步变化的过程。

这种建模方法的核心特点在于：静态文件中只保存高层参数，而运行时样本通过场景模板派生生成。候选站点并不是在数据文件中逐坐标列举，而是根据场景规模约束在区域网格中动态生成；用户位置和需求也不是固定表格，而是根据用户簇参数采样得到。这样既降低了静态文件冗余，也保留了足够的场景多样性，使得同一场景模板可以支撑多轮训练、测试与仿真演示。

每个场景样本都由一组稳定字段构成，既包含静态背景，也包含直接参与部署决策的参数。场景顶层字段主要包括标识信息、区域网格、用户规模、候选站点规模、通信与广播模式、资源画像、用户簇、时间片状态、设备配置以及奖励配置。字段组织如表 1.3 所示。

## 1.3. 多体制通信与广播资源建模

当前数据集一共定义了 8 类通信制式和 4 类广播制式，已经满足“通信制式种类不少于 4 类”的建设要求。通信资源覆盖低频蜂窝广覆盖、高频热点增强、卫星回传、局部 WiFi 接入、短波保底链路和空中中继等能力；广播资源则覆盖卫星广播、地面广播、数字音频和应急喇叭等方式。总体统计见表 1.4。

**表 1.4 通信与广播制式总体统计**

| 类别 | 当前种类 | 作用说明 |
| --- | --- | --- |
| 通信制式 | `5G_600MHz`、`5G_700MHz`、`5G_mmWave`、`Mesh_UAV`、`Satellite_Ka`、`Satellite_Ku`、`Shortwave_HF`、`WiFi6` | 覆盖蜂窝、卫星、WiFi、短波与空中中继资源。 |
| 广播制式 | `digital_audio`、`emergency_loudspeaker`、`satellite_broadcast`、`terrestrial_dtv` | 覆盖灾情播报、公众预警和保底广播能力。 |

通信资源和广播资源在场景中的作用并不相同。通信资源主要承担双向接入、回传和业务承载任务，广播资源主要承担灾情播报、预警通知和大范围信息分发任务。通过分开建模，数据集能够同时支持“恢复用户接入”和“恢复信息覆盖”两类目标，而不把全部资源都简化成统一的带宽项。

设备层面，数据集没有把“资源制式”和“设备类型”混为一谈，而是单独定义了设备画像，包括最大吞吐能力、最大服务人数、设备成本、带宽成本以及支持的制式列表。当前三个场景合计定义了 14 条设备配置，去重后共涉及 9 类设备键。该设计使得部署策略不仅需要考虑资源能力，还必须考虑设备容量与成本约束。

## 1.4. 通信资源变化时序指标

资源状态变化是数据集的核心内容之一。每个场景当前都设置 3 个关键时间片，分别对应灾后初始受损阶段、应急资源快速恢复阶段和阶段性稳定阶段。每个时间片同时包含通信侧的 `available_bandwidth` 与 `availability`，以及广播侧的 `available_bandwidth` 与 `coverage`。字段含义见表 1.5。

**表 1.5 关键时间片状态字段说明**

| 字段 | 所属对象 | 含义 | 单位或范围 |
| --- | --- | --- | --- |
| `available_bandwidth` | 通信 / 广播 | 当前时刻可用带宽容量 | Mbps |
| `availability` | 通信 | 当前制式可用性或在线概率 | 0–1 |
| `coverage` | 广播 | 当前广播资源的有效覆盖比例 | 0–1 |
| `coverage_radius` | 通信画像 | 覆盖半径 | 网格距离 |
| `max_bandwidth` | 画像参数 | 理论最大带宽 | Mbps |
| `recovery_speed` | 通信画像 | 恢复速度系数 | 0–1 |
| `latency_ms` | 广播画像 | 链路时延 | ms |

需要特别说明的是，关键时间片数量并不等于场景的最大步数。最大步数描述的是单次交互长度，而关键时间片只提供阶段性资源状态模板。在当前环境实现中，每执行一步，时间片索引都会向后推进 1；当推进到最后一个时间片之后，后续步骤会继续沿用末阶段状态，而不会再生成新的恢复阶段。因此，当前版本属于离散阶段恢复模型，适合表达“从受损到恢复”的总体过程，但尚不能替代高频连续监测数据。

为了更直观地体现不同灾害场景中的资源差异，表 1.6 给出了三个场景在灾后初始阶段的通信动态容量。动态容量采用“可用带宽 × 可用性”的方式估算，用于描述资源在初始受损时的即时有效能力。

**表 1.6 三个场景在灾后初始阶段的通信动态容量**

| 场景 | 主要制式 | 动态容量结果（Mbps） |
| --- | --- | --- |
| `typhoon_residual` | 5G_600MHz / 5G_700MHz / Satellite_Ka / WiFi6 / Shortwave_HF | 36.0 / 42.0 / 54.0 / 5.0 / 12.0 |
| `flood_no_residual` | 5G_700MHz / Satellite_Ka / WiFi6 / Shortwave_HF / Mesh_UAV | 24.0 / 61.6 / 2.0 / 9.0 / 20.0 |
| `earthquake_residual` | 5G_600MHz / 5G_mmWave / Satellite_Ku / WiFi6 / Shortwave_HF | 24.5 / 40.0 / 82.8 / 9.0 / 10.92 |

从上述结果可以看出，洪水和地震场景在初始阶段更依赖卫星链路提供稳定骨干能力，而地面蜂窝和局部热点资源通常需要随着恢复过程逐步发挥作用；台风场景则表现出“公网残损但尚有协同恢复基础”的特点。

## 1.5. 用户需求、空间网格与候选部署点

用户需求采用用户簇方式建模，而不是以逐用户静态记录方式保存。每个用户簇由中心坐标、影响半径、空间密度和需求强度构成，用于描述灾后人口向安置点、港口、核心城区和村落等区域聚集后的空间分布特征。用户簇的作用在于提供“需求热点”而非固定用户表，从而使同一场景模板在多次运行中能够生成分布相近但不完全相同的样本。

候选站点也采用参数化方式表达。数据集中只保存候选站点数量，而不直接写出完整坐标列表。运行过程中，系统会根据场景网格和数量约束生成候选部署点；用户位置与需求强度则依据用户簇参数进行动态采样。对于存在残余网络的场景，当前默认实现会在初始状态中随机保留一部分用户处于已连接、已广播覆盖状态，用于近似表示“仍有部分公网或残余链路可利用”的条件；这并不等同于已经给出完整的残余基站拓扑。由此可见，数据集保存的是场景生成规则，而不是一次性展开的静态观测全集。

除主场景模板外，数据集中还提供 5 个 Mahimahi 示例链路文件，分别对应应急指挥链路、受损站点链路、洪灾应急链路、巡逻车辆链路和临时中继链路。它们采用统一的时间戳格式记录数据包传输机会，主要用于链路容量回放和网络仿真演示，不直接参与主场景模板中的通信恢复决策。其统计信息见表 1.7。

当前版本数据集的主要特点在于结构清晰、参数集中、场景语义明确，并且能够同时表达通信资源、广播资源、设备能力、恢复阶段和奖励偏好。通过场景模板化设计，数据体积得以保持在较小范围内，但运行时仍可派生出大量样本，适合资源调度类任务的训练和验证。

**典型场景详细说明**

为便于理解场景模板的实际含义，本节对三个场景分别进行展开说明。需要强调的是，这些场景并不是对某一具体灾害现场的逐站逐链路复制，而是围绕典型灾害条件、典型区域功能区和典型资源组合建立的任务模板。它们的价值不在于复刻某一次真实事故全过程，而在于为应急通信资源部署问题提供结构完整、约束清晰、可反复训练的实验环境。

**台风残余网络场景**

`typhoon_residual` 场景以珠海沿海救灾区块为背景，网格规模为 24 × 24，共 576 个网格单元。场景中保留部分残余公网，因此重点不是从完全断网状态恢复，而是在公网受损、回传能力下降、局部热点需求快速上升的情况下，如何联合使用低频蜂窝、卫星回传、WiFi 热点和短波链路实现高效恢复。其典型区域标签包括“沿海居民聚集带”“港口作业区”和“山地安置点”，分别对应人口密集区域、物资调运区域和安置收容区域。这样的区域组合使得场景既存在广覆盖需求，也存在局部高吞吐需求和保底链路需求。

从用户簇分布看，该场景设置了 3 个需求簇。沿海居民聚集带半径为 4.0，密度权重为 0.35，人均需求强度为 15 Mbps；港口作业区半径为 6.0，密度权重为 0.40，需求强度为 20 Mbps；山地安置点半径为 5.0，密度权重为 0.25，需求强度为 8 Mbps。由此可以看出，港口作业区虽然不是唯一的需求中心，却具有最高的聚集密度和最高的平均需求，适合承载视频回传、物资调度和指挥协调类业务；山地安置点则强调覆盖连续性与基础接入能力，其需求强度相对较低，但对链路稳定性要求更高。

在通信资源配置上，该场景提供 `5G_600MHz`、`5G_700MHz`、`Satellite_Ka`、`WiFi6` 和 `Shortwave_HF` 五类通信制式。其中，`5G_600MHz` 和 `5G_700MHz` 共同承担低频广覆盖角色，理论最大带宽分别为 180 Mbps 和 200 Mbps；`Satellite_Ka` 的理论带宽为 90 Mbps，但可用性较高，适合作为灾后初期稳定骨干；`WiFi6` 负责局部热点补盲和容量扩展；`Shortwave_HF` 以较低带宽换取更高韧性，适合保底通信。广播侧则配置 `terrestrial_dtv`、`satellite_broadcast` 和 `digital_audio` 三类资源，用于支撑不同范围和时延要求下的灾情播报。

从时间片状态变化看，该场景表现出较为典型的“残余公网逐步恢复”特征。`5G_700MHz` 的可用性由 0.35 上升到 0.72，可用带宽由 120 Mbps 上升到 180 Mbps；`5G_600MHz` 的可用性由 0.40 上升到 0.75，可用带宽由 90 Mbps 上升到 150 Mbps；`Satellite_Ka` 始终保持较高可用性，从 0.90 提升至 0.98；`WiFi6` 则由 20 Mbps、0.25 的初始状态逐步恢复到 100 Mbps、0.60。这说明在台风场景中，卫星回传在早期承担稳定骨干角色，而地面蜂窝和局部热点在中后期逐步恢复并接管主要承载任务。

设备配置层面，该场景包含 4 类设备：应急宏站、卫星 Ka 中继、WiFi6 快速热点和短波应急台。应急宏站单设备最大吞吐 260 Mbps，可服务 180 人，设备成本系数为 1.0；卫星 Ka 中继最大吞吐 140 Mbps，可服务 110 人，但设备成本达到 1.6，带宽成本也最高；WiFi6 快速热点成本较低，但用户承载能力和覆盖半径均较小；短波应急台可服务人数高，但吞吐上限仅 25 Mbps。四类设备形成了较明确的成本梯度和能力梯度，能够支持“广覆盖优先”“低成本优先”“带宽优先”等不同部署偏好。

奖励配置方面，台风场景的默认模式为 `coverage_balance`，其主要目的是在覆盖、吞吐、广播和成本之间形成折中。除默认模式外，还提供 `cost_priority`、`coverage_priority` 和 `bandwidth_priority` 三类奖励配置，分别对应物资紧缺、快速恢复覆盖和面向高吞吐链路的不同目标。由于台风场景本身带有残余网络条件，因此同一套资源模板可以在不同奖励权重下呈现明显不同的部署倾向，是当前数据集中最适合作为综合基线的场景。

**洪水无残余网络场景**

`flood_no_residual` 场景对应洞庭湖城郊易涝区块，网格规模为 20 × 20，共 400 个网格单元。与台风场景不同，该场景显式设定为无残余公网，意味着灾后初始状态中传统地面网络几乎无法承担主要承载任务。场景中的典型区域标签包括“江滩村落”“湖滨新城”和“防洪堤后居民区”，三者分别代表分散乡村需求、城郊集中居住需求和临时安全区域需求。洪水场景的任务重点不在于公网残损后的协同恢复，而在于如何在基础设施大面积失效的前提下，依靠卫星回传、临时中继和局部热点实现从零起步的快速建链。

该场景设置了 3 个用户簇。江滩村落的簇半径为 5.0，密度权重为 0.40，需求强度为 12 Mbps；湖滨新城半径为 4.4，密度权重为 0.32，需求强度为 14 Mbps；防洪堤后居民区半径为 4.0，密度权重为 0.28，需求强度为 9 Mbps。相比台风和地震场景，洪水场景的需求强度整体偏中等，但需求分布更强调“多点分散 + 局部集中”共存，适合检验策略在分布式部署和补盲覆盖上的适应能力。

通信资源方面，该场景配置 `5G_700MHz`、`Satellite_Ka`、`WiFi6`、`Shortwave_HF` 和 `Mesh_UAV` 五类制式。`5G_700MHz` 仍承担广覆盖职责，但在无残余网络条件下初始作用受限；`Satellite_Ka` 是最关键的稳定骨干资源；`Mesh_UAV` 在该场景中的加入具有特殊意义，它既可承担空中中继，也可承担局部覆盖扩展，是洪水场景区别于其他场景的重要特征；`WiFi6` 和 `Shortwave_HF` 分别承担局部高效接入和低速保底通信任务。广播侧采用 `digital_audio` 和 `emergency_loudspeaker` 两类资源，体现洪水环境中轻量级广播方式的现实适用性。

时间片变化显示，该场景在初始阶段对卫星和空中中继依赖更重。`Satellite_Ka` 在初始阶段的动态容量达到 61.6 Mbps，是最稳定的关键链路；`Mesh_UAV` 为 20.0 Mbps，显著高于 `WiFi6` 的 2.0 Mbps 和 `Shortwave_HF` 的 9.0 Mbps；`5G_700MHz` 虽然理论能力较强，但在初始阶段动态容量仅为 24.0 Mbps，说明其仍需依赖恢复过程逐步发挥作用。进入后续时间片后，`WiFi6` 和 `5G_700MHz` 的带宽与可用性均有所提升，但卫星和中继资源仍保持较高优先级。由此可见，该场景天然适合检验“从零开始构建链路”时的决策逻辑。

设备配置方面，洪水场景包含防洪宏站、卫星 Ka 中继、WiFi6 便携热点、短波增程台和 Mesh UAV 共 5 类设备。与台风场景相比，这里的卫星中继成本更高，达到 1.7；Mesh UAV 的最大吞吐为 70 Mbps、最大服务人数为 60，设备成本为 0.75，体现了其介于热点设备与骨干设备之间的中间属性；短波增程台成本最低，但吞吐能力仍然有限。设备和资源的这种组合，迫使策略在覆盖连续性、成本控制和承载能力之间作出更精细的平衡。

奖励配置中，洪水场景默认模式为 `cost_priority`。这是因为洪水场景往往意味着物资和部署条件同时受限，低成本快速建立基础覆盖通常比追求单点高吞吐更重要。尽管如此，该场景同样保留 `coverage_balance`、`coverage_priority` 和 `bandwidth_priority` 三种补充配置，用于模拟救援阶段、保障阶段和业务强化阶段的不同策略目标。相比其他场景，洪水场景在奖励层面的重点更偏向资源紧约束条件下的部署效率问题。

**地震残余网络场景**

`earthquake_residual` 场景以川西震后山区为背景，网格规模为 22 × 22，共 484 个网格单元。该场景具有明显的山区语义和残余网络特征，典型区域标签包括“县城核心区”“山脊村落”和“河谷安置点”。县城核心区通常承载较高业务需求和较高热点密度；山脊村落则强调长距离、弱覆盖环境下的保底联通；河谷安置点兼具密集接入和相对受限的地形条件。相比台风和洪水场景，地震场景更适合考察高带宽热点资源与高韧性广域资源的协同部署问题。

用户簇方面，县城核心区半径为 5.0，密度权重为 0.33，需求强度为 16 Mbps；山脊村落半径为 5.6，密度权重为 0.30，需求强度为 18 Mbps；河谷安置点半径为 4.0，密度权重为 0.25，需求强度为 10 Mbps。山脊村落虽然不是最密集的簇，但需求强度最高，说明场景在设计上有意引入“高需求但覆盖困难”的目标区域，以提升策略学习的难度和现实感。

该场景的通信制式由 `5G_600MHz`、`5G_mmWave`、`Satellite_Ku`、`WiFi6` 和 `Shortwave_HF` 构成。与前两个场景相比，地震场景最大的差异是引入了 `5G_mmWave` 和 `Satellite_Ku`。其中，`5G_mmWave` 理论最大带宽高达 500 Mbps，但覆盖半径仅为 1.2，且初始可用性较低；`Satellite_Ku` 理论最大带宽 120 Mbps，恢复速度和可用性均较高，是山地条件下最稳定的骨干链路。`5G_600MHz` 提供必要的广覆盖能力，`WiFi6` 用于局部补盲，`Shortwave_HF` 用于超视距保底通信。广播侧采用 `satellite_broadcast`、`digital_audio` 和 `emergency_loudspeaker` 三类资源，对应广域信息分发、音频播报和近距离预警通知。

从初始时间片看，该场景的动态容量分布具有强烈的“高峰值热点 + 稳定骨干 + 保底链路”特征。`Satellite_Ku` 的动态容量达到 82.8 Mbps，是最稳定且最强的初始资源；`5G_mmWave` 虽然理论带宽极高，但因初始可用性仅 0.20，其动态容量为 40.0 Mbps；`5G_600MHz` 为 24.5 Mbps，体现出广覆盖资源受灾后恢复进度限制；`WiFi6` 与 `Shortwave_HF` 分别为 9.0 Mbps 和 10.92 Mbps。随着恢复过程推进，`5G_mmWave` 的带宽和可用性同步提升，适合在后期承担县城核心区等热点区域的容量增强任务。

设备配置方面，地震场景定义了抗震宏站、mmWave 微站、卫星 Ku 中继、WiFi6 补盲热点和短波超视距台 5 类设备。mmWave 微站的最大吞吐高达 520 Mbps，但用户容量只有 60，设备成本为 1.2，说明其定位是高价值热点增强设备而非广域基础设施；卫星 Ku 中继设备成本达到 1.8，是整个数据集成本最高的设备之一，但其容量和稳定性也最强；短波超视距台服务人数上限高达 230，适合承担极端条件下的基本联通任务。设备结构的这种差异，使地震场景在资源选择和部署顺序上具有更强的组合复杂度。

奖励配置层面，地震场景默认模式为 `coverage_priority`，这与余震频发、交通受阻和区域补盲优先的任务背景相一致。尽管 mmWave 和卫星资源能够提供较强吞吐能力，但在灾后初期，大面积恢复覆盖往往比少数热点的高带宽承载更重要。为适应不同阶段需求，该场景仍保留 `coverage_balance`、`cost_priority` 和 `bandwidth_priority` 三类补充配置，用于表示“折中恢复”“设备数量受限”和“高清视频/遥测回传优先”等不同运行目标。

## 1.6. 面向强化学习训练的任务封装

本数据集服务的核心任务不是传统分类或检测问题，而是多制式应急通信与广播资源的联合恢复与部署决策。场景模板中的用户规模、候选站点数量、通信模式、广播模式、设备画像、时间片状态和奖励配置共同决定了任务难度和优化方向。通过这些信息，可以在不同灾害场景下构建“覆盖优先”“成本优先”“带宽优先”等不同偏好的策略学习任务。

从当前项目的环境实现看，每个场景模板都会被封装为一个可直接运行的强化学习任务。状态空间以用户特征、候选站点部署状态、通信制式可用性、广播制式覆盖状态以及剩余部署预算共同组成；动作空间围绕“在某个候选位置部署某种通信模式并激活某种广播模式”展开；状态转移则由时间片推进、设备部署结果、用户接入变化和广播覆盖变化共同决定。由于场景中同时存在通信模式、广播模式和设备成本约束，因此同一场景既不是纯粹的覆盖优化问题，也不是单一的吞吐最大化问题，而是一个带有阶段性资源变化和多目标奖励约束的联合决策任务。

进一步对应到当前环境封装方式，动作空间本质上是一个离散组合空间，其大小由“候选站点数量 × 通信模式数量 × 广播模式数量”共同决定；执行一次动作后，环境会同步更新通信部署掩码、广播激活掩码和剩余部署预算。观测空间则不仅包含用户位置归一化结果、用户需求和连通状态，还包含当前通信资源可用带宽、可用性、广播覆盖率以及部署利用率等特征。这意味着当前数据集并非只为离线统计分析准备，而是已经和训练环境的数据结构保持一一对应，能够直接支撑策略学习、评估回放与前端联调。

从训练角度看，用户规模决定状态空间大小，候选站点和资源模式共同决定动作空间大小，时间片状态决定资源随恢复阶段变化的边界条件，设备画像决定部署成本和容量上限，奖励配置决定多目标优化时的权重平衡。正因为数据集同时保存了这些结构化约束，它不仅能支撑训练与评估，还能支撑前端演示、回放导出和组网方案分析。在当前实现中，残余网络场景会在初始状态中保留一部分已连接用户，无残余网络场景则从更受损的初始条件开始；这使得同一算法能够在不同起点条件下学习“协同恢复”和“从零建链”两类不同策略。

当前数据集的每个场景均定义 4 套奖励配置，分别为 `coverage_balance`、`cost_priority`、`coverage_priority` 和 `bandwidth_priority`。四类配置虽然字段结构一致，但语义重心并不相同。`coverage_balance` 适合用作综合基线，强调覆盖、吞吐、广播和成本之间的折中；`cost_priority` 强调设备成本和带宽成本控制，适合物资紧张、交通受限或快速部署阶段；`coverage_priority` 用于强调用户接入恢复和盲区补齐；`bandwidth_priority` 则面向视频回传、遥测数据上传、指挥链路和热点承载等对吞吐较敏感的业务需求。

奖励配置的引入，使得同一套资源模板可以在不同目标偏好下形成不同的训练任务。例如在台风场景中，`coverage_balance` 更适合刻画常规综合恢复策略，而 `bandwidth_priority` 更适合考察港口作业区或高密度业务区域的资源调度倾向；在洪水场景中，默认 `cost_priority` 反映了应急阶段物资和部署能力受限的现实约束；在地震场景中，默认 `coverage_priority` 则更符合余震频发、道路阻断和大面积盲区待恢复的任务特点。

**表 1.8 三类场景默认奖励模式**

| 场景 | 默认奖励模式 | 配置含义 |
| --- | --- | --- |
| `typhoon_residual` | `coverage_balance` | 覆盖、吞吐、广播和成本折中。 |
| `flood_no_residual` | `cost_priority` | 在资源紧张条件下优先控制设备与带宽成本。 |
| `earthquake_residual` | `coverage_priority` | 以快速补盲和大面积覆盖恢复为主。 |

从权重构成上看，奖励体系主要围绕覆盖权重、带宽权重、吞吐权重、广播权重、设备成本权重和带宽成本权重 6 个维度展开。其设计意义在于：覆盖权重直接影响新增接入用户的收益比例；带宽和吞吐权重决定系统对高容量链路的偏好程度；广播权重决定灾情通知、预警播发等能力是否被充分鼓励；设备和带宽成本权重则用于抑制“无限堆设备”或“盲目选择高成本链路”的策略倾向。由于所有场景都采用统一的权重字段结构，因此数据集在保持语义一致性的前提下，能够通过数值差异表达各灾害场景的阶段性目标。

## 1.7. 数据集可扩展性与质量控制

数据集虽然采用模板化组织方式，但仍然需要保证结构一致和语义自洽。当前版本在数据质量控制上主要关注三类一致性。第一类是资源字段一致性，即场景中声明的通信制式必须在通信能力画像和时间片状态中出现，广播制式也必须在广播画像和广播时间片中出现。第二类是设备映射一致性，即通信制式所绑定的设备类型必须在设备配置表中存在，并且设备支持模式列表能够覆盖对应制式。第三类是时间片语义一致性，即可用带宽、可用性和覆盖率的变化应当符合灾害恢复逻辑，不能出现无解释的突变。

除了上述结构一致性外，数据集还强调任务语义一致性。例如，存在残余网络的场景应当体现“公网尚有部分协同能力”的背景，而无残余网络场景则应突出“从零开始恢复”的特点；广播资源的覆盖率不应在灾后初期就普遍高于通信资源的恢复上限，除非场景设定本身就是以卫星广播为主；高带宽资源在低可用性条件下应当体现出“理论能力强但即时有效能力未必高”的特征。只有在这些语义层面保持一致，数据集才能真正为资源调度问题提供有价值的训练条件。

静态数据文件体积较小是当前数据集最容易被误解的地方。其原因并不在于数据缺失，而在于数据被组织成了高层场景模板。用户规模、候选站点数量、用户簇、设备画像和关键时间片并不是一次性展开为固定样本，而是在每次交互开始时重新生成运行时实例。对于同一个场景模板，多次运行将产生不同的用户坐标、不同的需求扰动以及不同的候选站点布局，因而即使只有 3 个场景模板，也可以派生出远多于 3 条静态记录的训练样本序列。

从样本序列角度看，一个场景模板对应的并不是一条数据，而是一组可以重复生成的决策过程。每个过程都包含初始状态、若干部署动作、中间状态变化和最终覆盖结果。由于候选站点、用户分布和残余网络状态都具有一定随机性，同一场景在多轮训练中不会完全重复，从而提升了策略学习时的泛化能力。对于资源调度问题而言，这种“模板固定、样本动态”的方式比纯静态数据表更有利于构建高多样性的实验环境。

当前数据集适合用于以下几类任务：第一，多制式应急通信资源部署策略训练；第二，通信与广播联合恢复任务评估；第三，不同奖励偏好下的多目标资源调度实验；第四，前端原型系统、回放系统和链路仿真系统的联调展示；第五，广播通信融合组网方案的辅助分析。由于数据集本身包含区域网格、用户簇、设备画像和时间片状态，因此既适合策略学习，也适合可视化和方案导出。

但在适用范围之外，也应看到其局限性。当前版本并不是全国尺度、多灾种、长时间序列的开放式原始数据集，也不直接提供固定 benchmark 所需的大规模逐用户标注数据。若用于跨区域泛化研究、精细网络规划或长周期恢复建模，还需要进一步扩展场景数量、增加时间片密度、固化候选站点和残余网络结构，并在模板之外导出更稳定的实例化样本。

数据集后续扩展可以围绕四个方向展开。第一，扩展灾害类型和场景数量，在现有台风、洪水、地震基础上增加暴雨、泥石流、山火、寒潮等场景，以丰富任务分布。第二，提升时序分辨率，将当前 3 个关键时间片扩展为更长的恢复序列，用于表达从分钟级到小时级的资源恢复过程。第三，增强空间固定性，将候选站点、残余基站和关键回传节点由“数量约束”逐步扩展为“实例清单”，以形成更稳定的 benchmark。第四，扩展数据输出形式，在保留模板结构的基础上，增加固定 episode 导出、统计摘要导出和训练/验证/测试划分导出，从而支撑更规范的数据集使用流程。

当前版本数据集的主要特点在于结构清晰、参数集中、场景语义明确，并且能够同时表达通信资源、广播资源、设备能力、恢复阶段和奖励偏好。通过场景模板化设计，数据体积得以保持在较小范围内，但运行时仍可派生出大量样本，适合资源调度类任务的训练和验证。

与此同时，当前版本也存在边界条件。场景数量目前只有 3 个，灾害覆盖范围仍较有限；每个场景只设置 3 个关键时间片，时序分辨率偏低；用户与候选站点并非固定 benchmark 实例，而是按模板动态生成；残余网络建模仍然偏抽象，尚未展开成完整的残余设备拓扑。上述限制决定了当前数据集更适合作为研发验证和原型系统训练基础，而不是最终形态的大规模实测开放数据集。

极端灾害通信资源变化数据集通过场景模板方式，将灾害类型、区域网格、用户需求簇、多体制通信资源、广播资源、设备画像、恢复阶段和奖励配置统一组织到一个结构化样本体系中。该数据集在规模上保持紧凑，在表达能力上覆盖了灾后通信恢复任务所需的核心要素，能够支持多模态应急通信资源优化、联合覆盖恢复、策略训练、仿真演示和方案分析等多类任务。后续若继续扩展，可在保持当前结构稳定的基础上增加更多灾害场景、延长时间序列、固化候选站点与残余网络实例，从而逐步形成更完整的数据集体系。

从当前阶段看，场景模板式组织方式仍然具有明显优势。它能够以较低的数据维护成本支持策略迭代、界面联调和方案输出，同时也为后续扩展留下了足够空间。随着场景数量、时间片密度和残余拓扑结构的增加，该数据集可以逐步演化为更完整、更标准化的灾害通信资源数据集体系。
